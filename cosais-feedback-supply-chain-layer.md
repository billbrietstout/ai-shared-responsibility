# COSAiS AI Control Overlays feedback on the Supply Chain layer

COSAiS AI Control Overlays feedback on the Supply Chain layer (the development, training, and distribution of models: training data governance, model development security, model provenance and lifecycle, third-party models, datasets, and ML libraries).

From an OSCAL perspective, there are two gaps here.

First, model provenance attestation. SR-4 (Provenance) and CM-14 (Signed Components) are the natural anchors, but both have untyped ODPs, so neither can carry a measured objective. So an organization can say it implements SR-4 and CM-14 for model artifacts, but there is no measurement of what fraction of production model versions actually carry a valid attestation and current model card. Unsigned or stale-carded models reach production silently: a base model gets swapped, an adapter gets added, a hotfix version ships, and the attestation ratio drops with no control failing. For model artifacts the target should be 100% with zero error budget; a single unattested model in production is an unverifiable model in production.

Second, post-deployment model drift. Models degrade after deployment as input distributions shift, and the controls have nowhere to hold a bound. CA-7 (Continuous Monitoring) and SI-4 (System Monitoring) both resolve to cadence-only ODPs: they can say how often monitoring reports are produced, but not what the monitored metrics must hold, over what window, with what tolerated shortfall. CA-7's odp.01 (system-level metrics) is exactly the right hook, and it is untyped today. The worked example that shows the shape already exists in regulation: FDA's Predetermined Change Control Plan for AI-enabled device software declares performance and input-distribution bounds up front, and the measurable objective is the percent of monitored metrics remaining within declared bounds during the window. An organization can pass a CA-7 audit on report cadence while a deployed model has drifted well outside any bound anyone would accept.

Proposed enhancement: introduce coverage objective parameters on SR-4/CM-14 (attestation ratio) and typed metric bounds on CA-7 odp.01 (drift). Same shape as the other layers:

* Target value (e.g., 100% of production model versions attested; 100% of monitored metrics within declared bounds)
* Comparison operator ( = < > >= <= )
* Measurement window (e.g., rolling 30 days for attestation, rolling 7 days for drift). Not the same as ODP cadence; cadence sets how often a report is produced, the window is the period over which the ratio is computed.
* Reconciliation method (e.g., model registry scanned against the signing service, so unattested models are found by enumeration rather than self-report; monitoring pipeline output compared against pre-declared bounds, so the bounds cannot be adjusted after the fact)

Other AI related items at the Supply Chain layer which should also include coverage objectives:

* Training data lineage coverage: percent of training and fine-tuning datasets with verified source, licensing, and lineage records from raw data through final model. No 800-53 control models dataset lineage at all; SR-4 comes closest and is component-oriented. You cannot assess a model whose training data you cannot enumerate.
* Dataset integrity screening coverage: percent of training and fine-tuning data batches screened for poisoning and integrity before use. SI-7 has untyped ODPs and no concept of training data as a protected integrity class, even though poisoned data compromises every downstream deployment at once.
* Third-party model and dependency provenance: percent of base models, adapters, and ML libraries resolved from signed registries with a bill of materials covering model, datasets, and dependencies. SR-3 and SR-11 are cadence-only. Model supply chains now include artifacts (checkpoints, LoRA adapters, tokenizers) that traditional SBOM practice never sees.
* Pre-release adversarial testing coverage: percent of model releases red-teamed against known attack classes before release, per declared attack taxonomy. CA-8 is cadence-only with no parameter for attack classes covered; a model release is not a penetration test window.
* Evaluation regression coverage: percent of model releases passing the declared evaluation suite (capability, safety, and bias dimensions) before deployment, with results attached to the model card. No control treats an evaluation suite as a gating artifact.
* Vulnerability disclosure responsiveness: percent of reported model-level vulnerabilities triaged within a target period, with coordinated disclosure. IR-6 and RA-5 carry cadence, not response ratios, and neither recognizes model-level vulnerabilities (extractable training data, jailbreak classes, backdoored weights) as a category.
* Deprecation propagation coverage: percent of deprecated or vulnerable model versions removed or flagged in downstream deployments within a defined period. SA-22 (Unsupported System Components) has no ratio to carry, and model consumers rarely learn a base model was pulled.

One structural note that this layer makes obvious: across all four layers of this feedback series, every threshold control resolves to a live rev 5 anchor control, so catalog breadth is not the problem. The gap is uniformly parameter typing. The best any binding achieves is cadence-only. The fix is twofold: for the overlays, define ODPs structured as measured objectives (target, comparison, window, tolerated shortfall) wherever a control governs continuously measurable AI behavior; for OSCAL itself, add a typed parameter constraint (numeric, with unit and window semantics) so profiles can carry operational thresholds natively and a resolved profile can emit set-parameter values that provably match live monitoring configuration.
