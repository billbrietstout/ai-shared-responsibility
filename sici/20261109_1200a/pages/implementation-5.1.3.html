Implementation 5.1.3: Implement Cryptographically Verifiable Identities and Automated Mutual Authentication

AI entities should authenticate using cryptographic credentials (such as certificates or signed tokens) rather than static passwords, and require the receiving system to verify the AI entity’s identity in return before exchanging data or commands. Where a legacy device cannot authenticate for itself, a gateway in front of it can perform the authentication, so that it occurs outside the control device (see CISA, Adapting Zero Trust Principles to Operational Technology). Binding the tokens an SI entity presents to that entity, and limiting where each token is accepted, can help keep a token captured at one tool from being replayed from elsewhere. This helps prevent a spoofed component from posing as a trusted AI agent (this is a gap that default or reused credentials on exposed devices can open).

Where environments and components hold distinct credentials, it can also catch a misconfigured connection, such as an agent pointed at a test instance rather than the production system, before data or commands are exchanged. Cryptographic identities depend on managing the keys and certificates behind them, including issuance, rotation, revocation and recovery. Plan that management before relying on these identities, since expired, lost or compromised credentials can lock out legitimate components or be used to impersonate them. Organizations with an established public key infrastructure or secrets management service can build on it for SI entities, though the volume and short lifetimes of SI credentials add to its workload. Some frameworks, such as CoSAI’s Agentic Identity and Access Management, limit long-lived static credentials to legacy or low-risk cases. SI entities should use short-lived credentials by default, and this matters most for higher-risk SI entities. For higher-risk SI entities, short-lived credentials should also carry fresh claims about the entity’s current state, such as its model version and active task, for the receiving system to check at each critical operation.

Decisions for the Organization:

  • Which SI entities count as higher-risk and carry short-lived credentials bound to their current state?
  • Which legacy devices authenticate through a gateway in front of them?
  • Who manages the keys and certificates behind SI entity identities, and with what resources?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control IA-9, Service Identification and Authentication, uniquely identifies and authenticates defined services and applications before communications are established, using methods that include code signing and digital certificates, which is the control applicable when an AI agent or tool connects to another system. Control enhancement IA-3(1), Cryptographic Bidirectional Authentication, covers the mutual, cryptographically based authentication this Implementation calls for where the AI entity runs on a device.
  • Guidance NIST SP 800-53 Rev. 5, Release 5.2.0, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control enhancement IA-13(2), Verification of Identity Assertions and Access Tokens, added to the catalog after the 2020 Rev. 5 publication and included in Release 5.2.0, calls for the source and integrity of identity assertions and access tokens to be verified before access is granted, and its discussion includes verification of their digital signatures and metadata. IA-13(1), Protection of Cryptographic Keys, covers the keys that sign them. IA-13(2) specifies the receiving system’s check on a signed credential presented by an AI entity, and IA-13(1) protects the keys that check relies on.
  • Guidance Agentic Identity and Access Management, Workstream 4: Secure Design Patterns for Agentic Systems, version 1.0, 20 March 2026, from the Coalition for Secure AI, an OASIS Open Project. Their Section 3.3, Authentication, matches the mechanism to the agent’s autonomy level and risk tier: narrowly scoped service accounts or API keys with aggressive rotation for legacy or low-risk cases only, to be phased out over time; short-lived ephemeral identities as the preferred default; and hardware-backed keys with attestation for high-risk, high-capability agents. It adds that short-lived credentials and periodic attestations should emit fresh claims about the agent’s state, such as model version and active task. Their Section 3.5, under Lifecycle requirements, states that high-risk agents MUST use short-lived credentials and, where feasible, strong attestation.
  • Incident Report IRGC-Affiliated Cyber Actors Exploit PLCs in Multiple Sectors, Including US Water and Wastewater Systems Facilities, AA23-335A, originally published 1 December 2023 and updated 18 December 2024, from CISA and partners. Reports that between November 2023 and January 2024 the actors compromised at least 75 internet-connected PLCs, at least 34 of them in the water and wastewater sector, by authenticating to devices that had a default password or no password. This is an instance of the gap from default or reused credentials that this Implementation names.
  • Guidance Adapting Zero Trust Principles to Operational Technology, 29 April 2026, from CISA, the Department of War and the Department of Energy with partners. The section on Secure Communication, Data Integrity, and Encryption notes that most OT networks operate without authentication, and that where secure protocol support is unavailable, legacy protocols can be wrapped in secure tunnels, for example through TLS-enabled gateways, so that authentication occurs outside the control devices. This bears on authenticating SI entities to legacy devices.
  • Guidance Model Context Protocol (MCP) Security, Workstream 4: Secure Design Patterns for Agentic Systems, 8 January 2026, from the Coalition for Secure AI, an OASIS Open Project. Section 3.2.2, Secure Delegation and Access Control, recommends short-lived tokens that support proof-of-possession (DPoP, RFC 9449) against replay attacks, and token exchange (RFC 8693) for accountability. This bears on binding the tokens an SI entity presents to that entity.
