Implementation 12.2.1: Deterministic and Rule-Based Guardrails

(Referencing Task 3.2: Implement Independent Guardrails for SI Outputs, in particular Implementation 3.2.5: Artifact Verification) Verify that all AI-generated executable artifacts (like network configurations or PLC logic) pass through independent, deterministic verifiers, such as static code analyzers, syntax-tree-aware validators that check the parsed structure of code and configurations rather than their text, or schema validators, to check that they meet hard-coded safety constraints. Static analysis rules for weaknesses such as command injection and hardcoded secrets are worth including, since these have been found more often in AI-generated code than in human-written code (see Cotroneo et al. 2025). Passing these checks shows that the artifact meets the constraints tested, not that it is correct overall (see Implementation 12.2.3: Validation Against Tacit and Formal Requirements). Where no deterministic verifier exists for the target language, as can be the case for some PLC programming languages, a minimal implementation is a structured checklist review against the same constraints by a reviewer independent of the generation, combined with the isolated execution testing in Implementation 12.3.1: Isolated Execution Testing (Sandboxing), with the gap recorded so that a verifier can be adopted when one becomes available. Appropriate meta-safeguards should be in place if these independent, deterministic verifiers are, themselves, written with the assistance of AI. Where generated code names external packages or libraries, check that each one is the intended package before it is adopted. Code-generating LLMs can suggest plausible package names that do not exist, and attackers can register those names in advance. A check that a suggested name exists in a public repository is not sufficient on its own, because an attacker may already have published a package under that name (see Spracklen et al. 2025).

A failed check can block promotion of the artifact unless an exception is approved and recorded. The rule sets that these verifiers apply encode safety constraints, and they can be kept under version control and reviewed when the process or the requirements change. For PLC logic, as an example, checks can confirm that referenced tags and addresses exist in the approved input and output list, that setpoints and timers fall within the safe operating envelope, and that the logic does not write to safety tags, force values or bypass interlocks. For network configurations, checks can confirm that no rule opens a path that the zone and conduit policy forbids. The rule sets show which constraints are checked automatically and which are not, so an attacker who obtained them could shape an artifact to pass. They can be protected under the organization’s existing information classification and handling practice, like other descriptions of its safety constraints.

Decisions for the Organization:

  • Who may approve an exception when a deterministic check fails, and how is it recorded?
  • Where no deterministic verifier exists for a target language, what review is used until one is adopted?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control enhancement SA-11(1), Static Code Analysis, has the organization require developers to use static code analysis tools to identify common flaws and document the results, and notes that it is most effective when each code change is scanned automatically, which is the deterministic verification this Implementation applies to AI-generated code and configurations.
  • Research Spracklen, J., Wijewickrama, R., Sakib, A. H. M. N., Maiti, A., Viswanath, B., and Jadliwala, M., We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs, August 2025, from the Proceedings of the 34th USENIX Security Symposium, USENIX Association. Across 16 code-generating models, it reports average hallucinated-package rates of at least 5.2% for commercial and 21.7% for open-source models. Section 5.3 finds that many hallucinated names recur when the same prompt is repeated, a persistence that makes them more useful to an attacker. Section 1 notes that comparing a generated name with a list of known packages does not detect an attack, since an adversary may already have published the hallucinated package. This bears on the package check in this Implementation.
  • Research Cotroneo, D., Improta, C., and Liguori, P., Human-Written vs. AI-Generated Code: A Large-Scale Study of Defects, Vulnerabilities, and Complexity, preprint arXiv:2508.21634v1, August 2025, from the University of Naples Federico II. Comparing over 500,000 Python and Java samples, it finds that AI-generated code more often triggers high-risk weaknesses, including command injection and hardcoded secrets. Section VI notes that static analysis covers syntactic and structural aspects and excludes runtime behavior, context-specific errors and deeper semantic correctness. Both findings bear on what a deterministic verifier can show for generated code.
