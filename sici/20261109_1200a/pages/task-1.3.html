Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle

Testing repeated across the lifecycle helps an organization confirm whether an SI system still meets its requirements after acceptance, as the system’s behavior and the conditions of its use change. Develop and execute a systematic testing, evaluation, validation, and verification (TEVV) program that assesses AI performance against established requirements, as defined in Task 1.1: Identify Current Requirements and, in particular, Implementation 1.1.2: Structured Requirements Mapping, at each stage of the asset lifecycle, and against previous baselines (if any). The system under test should be the AI system as deployed, including, where present, the model version, prompts and configuration, retrieval and data pipelines, tools, safety wrappers and interfaces, together with the operators who act on its outputs.

This Task serves as the anchor for TEVV considerations throughout this profile. It supports the generation of verifiable, audit-ready evidence, with re-evaluation as environments change handled under Implementation 2.3.4: Recurrent Risk Evaluations. Specialized applications of this framework appear throughout this profile. For example, Task 2.3: Establish Protocols for and Regularly Perform Systematic and Achievable Testing, Evaluation, Validation, and Verification (TEVV) extends TEVV to anomaly and edge-case behavior. Implementation 4.1.3: Regularly Practice and Evaluate Intervention Processes applies TEVV to override and intervention procedures. Implementation 7.5.2: Perform Automated “Champion-Challenger” Assessment applies it to champion-challenger assessment, and Task 11.4: Establish System Integrity Re-Validation and Re-Commissioning Protocols applies it to system re-commissioning.

Main Trustworthiness Contributions:

  • Valid: Contributes the evidence that a delivered system meets the requirements and operating envelopes set in Task 1.1: Identify Current Requirements, with scope, environment and pass/fail criteria fixed per lifecycle stage before testing begins (Implementation 1.3.1: Define TEVV Scope and Requirements per SI System), and with the conditions beyond which that evidence does not hold recorded alongside it. This Task does not cover detecting the loss of validity that appears only after the operating environment moves. For that, see Implementation 2.3.4: Recurrent Risk Evaluations for scheduled re-evaluation, and Task 3.4: Monitor for Anomalous SI Behavior for continuous runtime monitoring.
  • Safe: Contributes the verification that a system exceeding its defined boundaries derates or transitions predictably, and the rule that a system whose evidence does not support autonomy is held in a more restrictive oversight mode, with the oversight capacity that mode needs confirmed as available rather than assumed (Implementation 1.3.1: Define TEVV Scope and Requirements per SI System). This Task does not specify the fallback states themselves. For those, see Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior.
  • Transparent: Contributes the acceptance record: test plans, dataset provenance documentation, model cards and empirical results held as one package for regulatory audit, lifecycle review and post-incident evaluation (Implementation 1.3.4: Generate and Maintain Audit-Ready TEVV Evidence). This Task does not cover capturing what the system did in service. For that, see Practice 10: Implement Multi-Tiered SI System Logging and Audit Capabilities.

Trustworthiness Side Effects to Consider:

  • Secure: TEVV evidence records where the system was found weak, which conditions were not tested, and which assumptions the results depend on (Implementation 1.3.1 and Implementation 1.3.4). An attacker could use it to aim manipulated inputs or faults at the conditions known to be untested or poorly handled. Protecting that evidence is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Valid versus Safe: Where an application can sustain a planned outage, such as a report summarization tool or an off-peak batch process, testing during an authorized window yields evidence about the system that will actually run (Implementation 1.3.2: Categorization of Testing Environments). Where service delivery or a physical control loop cannot tolerate disruption, that evidence has to come instead from staging mirrors, hardware-in-the-loop rigs, simulators or digital twins, whose behavior may differ from the live system in ways the test will not show. One way to balance this is to record the difference between the test environment and the live system as a stated limit on the evidence, and to bound what is claimed from it. Others include raising fidelity for the specific behaviors that carry the most consequence, or confirming a narrow set of them live during scheduled downtime.

Related AI RMF Subcategories Include:

  • MAP 2.3 (on applying scientific methodologies): This Task fixes TEVV scope, test environment and pass/fail criteria per lifecycle stage before testing begins, and keeps destructive and adversarial testing off live production paths, except during scheduled downtime as discussed in Implementation 1.3.1 and Implementation 1.3.2; it does not address the data availability, representativeness and suitability that MAP 2.3 also names. For those, see for example Task 7.2: Validate, Select, and Prepare Data for SI Systems.
  • MEASURE 1.3 (on involving independent assessors): This Task has the roles that design, execute, review and accept tests named, with their independence from the developer or supplier scaled to consequence (Implementation 1.3.1: Define TEVV Scope and Requirements per SI System); it does not cover setting up the consultation with affected communities that MEASURE 1.3 also names.
  • MEASURE 2.5 (on measuring validity and reliability): This Task demonstrates validity and reliability against the requirements and operating envelopes set in Task 1.1: Identify Current Requirements, and records the conditions beyond which that evidence does not hold; it does not cover detecting the loss of validity that appears only after the operating environment moves. For that, see for example Implementation 2.3.4: Recurrent Risk Evaluations.
  • MEASURE 2.6 (on measuring safety): This Task verifies that a system exceeding its defined boundaries derates or transitions predictably, and constrains it to a more restrictive oversight mode where the evidence does not support autonomy; it does not specify what the fallback states themselves should be. For that, see for example Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior.

Decisions for the Organization:

  • Where live testing is not possible, how much difference between the test environment and the live system is accepted? (see the Valid versus Safe tension in Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle)
  • Who staffs and funds TEVV across the lifecycle, including independent assessors and test environments, and what is done where that capacity is not available?

References:
The following references illustrate how different critical infrastructure sectors have formalized TEVV-equivalent processes. Readers should look for analogous frameworks within their own sector’s regulatory or standards environment.

  • Regulation DoD Manual 5000.101, “Operational Test and Evaluation and Live Fire Test and Evaluation of Artificial Intelligence-Enabled and Autonomous Systems,” December 9, 2024, a policy issuance of the United States Department of Defense, binding on DoD components. Section 4 sets out the process for operational and live fire test and evaluation of SI-enabled and autonomous systems.
  • Regulation DoD Directive 3000.09, “Autonomy in Weapon Systems,” January 25, 2023, from the same department. Section 3 covers verification and validation and testing and evaluation of autonomous and semi-autonomous systems.
