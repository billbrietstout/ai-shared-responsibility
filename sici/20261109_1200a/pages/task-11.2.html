Task 11.2: Define Manual and Alternative Operating Procedures for Long-Term Mission Continuity

A workable manual alternative helps make switching an SI system off a practical option when that is the right call, not only when the system stops by itself. Develop and document comprehensive “Manual Mode” instructions for running essential functions for extended periods without AI support. Organizations with established manual or emergency operating procedures for other equipment can build on those procedures for functions that now depend on SI. These playbooks should define orchestrated fallback pathways tailored to the system’s operational timeline: For critical systems requiring 24/7 availability, they should set out the process for a safe transition, without interrupting availability, to a legacy deterministic system where the organization has kept or prepared one. Keeping such a system ready has its own considerations, such as maintaining it and keeping its configuration current. For critical systems that do not need to be realtime (such as financial fraud queues, non-emergency triage systems, or administrative compliance tools), they should outline the protocols to safely pull the AI infrastructure offline while minimizing other risks, such as security and data corruption, and route accumulated tasks into structured manual workflows. This Task complements those of Practice 4: Define Procedures for Emergency Avoidance Override, Recovery, and Situational Awareness by providing the operational playbook for sustained, non-automated service delivery during a prolonged outage. Define in advance the conditions that call for a switch to these procedures and the role authorized to make it. The role authorized to make the switch needs the visibility to recognize those conditions, the authority to act on them, and support when the switch disrupts service. These conditions can include indications that the SI system is producing incorrect output or has been compromised, as well as loss of availability.

Main Trustworthiness Contributions:

  • Resilient: Contributes the playbook for running essential functions without the AI system for an extended period, from a transition to a legacy deterministic system without loss of availability to routing accumulated work into manual workflows, backed by a safe operating mode tested to last for the outage durations in the organization’s design basis (Implementation 11.2.2: Develop a Validated “Safe Operating Mode” that Depends Minimally on SI Infrastructure). This Task does not specify the immediate state the control system enters on disengagement, which Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior specifies.
  • Safe: Contributes the handover itself: a State-at-Handoff summary, paced acknowledgment of current states and incremental de-escalation, so that personnel taking over do not start cold (Implementation 11.2.3: Human Factors and Cognitive Transition Protocols for Control Handoffs), and a controlled shutdown where the fallback cannot be sustained (Implementation 11.2.4: Unplanned Shutdown and Controlled Isolation Protocols). This Task does not cover determining which processes allow time for a paced handover, which Task 4.5: Define Operational Regimes for Human-on-the-Loop and Human-Out-of-the-Loop Operation covers.

Trustworthiness Side Effects to Consider:

  • Secure and Reliable: Pulling AI infrastructure offline and moving work into manual workflows handles data and access outside their usual paths at a time of disruption, which exposes them to misuse and also to accidental loss, duplication or corruption as accumulated work is moved into manual queues. Handling data and access during the move is a matter for the organization’s existing data-handling, access-control, and change-control practice. What is specific to the SI system is reconciling the work it had queued or in progress with what moves to manual queues, so that none is lost or done twice; the State-at-Handoff summary in Implementation 11.2.3: Human Factors and Cognitive Transition Protocols for Control Handoffs can carry part of it.
  • Secure: The manual procedures, and the conditions that call for a switch to them, show how the organization runs essential functions without the SI system, how long a switch takes, and what triggers it. An attacker could use them to provoke a switch at a chosen moment, or to time an attack for when personnel are working manually and stretched. Implementation 11.2.1: Document Basic Manual Fallback Procedures for SI-Dependent Control Points asks for the procedures to be protected as sensitive information. How is a matter for the organization’s existing information classification and handling practice, balanced against keeping them at hand during an outage.

Trustworthiness Tensions to Balance:

  • Safe versus Safe: Where the process time constants allow it, a paced step-through that has personnel acknowledge active setpoints, pending approvals or triage states protects against taking control without context. Where the event is moving faster than that, the same pacing delays the takeover it is meant to make safe. One way to balance this is the condition already in Implementation 11.2.3: Human Factors and Cognitive Transition Protocols for Control Handoffs, applying bounded pacing only where Task 4.5: Define Operational Regimes for Human-on-the-Loop and Human-Out-of-the-Loop Operation shows the time constants permit; others include incremental de-escalation of the most urgent sub-system first, with the rest acknowledged afterward.

Related AI RMF Subcategories Include:

  • MANAGE 2.1 (on allocating resources): This Task covers the viable non-AI alternatives themselves, in documented manual steps and a validated safe operating mode for each essential function; it does not cover securing the personnel, tools and reserves needed to run them. For that, see for example Task 11.3: Pre-Allocate Operational Resources for Alternative Service Delivery.
  • MANAGE 2.4 (on decommissioning or superseding AI systems): This Task covers the protocols for taking AI infrastructure offline and handing operational authority to manual control for a sustained period; it does not cover the in-the-moment decision to override or disengage. For that, see for example Task 4.1: Establish “Break-Glass” Intervention Procedures.

Decisions for the Organization:

  • Which conditions call for the switch to manual procedures, and which role is authorized to make it?
  • Who writes and maintains the manual procedures, and how often are they checked against the current process?
  • If the preferred fallback, such as a legacy system, is unavailable when needed, what is the next option?

References:

  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. The Executive Summary, under “Maintain functionality during adverse conditions”, gives as an example of graceful degradation a move from full automation, through emergency operation with operators more involved, to manual operation with no automation. Section 6.2.4.5 lists “transitioning to manual operations” among OT response considerations and asks that response plans be kept on paper or offline.
  • Guidance NIST SP 800-218A, Secure Software Development Practices for Generative AI and Dual-Use Foundation Models: An SSDF Community Profile, July 2024, from NIST. Task RV.2.2 consideration C1 suggests being prepared to stop using an AI model at any time and to continue operations through other means until its risks are sufficiently addressed. This Task covers the procedures that make that preparedness real for essential functions over an extended period.
