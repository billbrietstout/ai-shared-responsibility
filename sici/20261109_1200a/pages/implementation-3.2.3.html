Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior

Defined fail-safe states let a process move to a known, reviewed condition when SI output cannot be trusted, rather than to whatever state the failure leaves behind. Define deterministic states the control system should enter when AI output violates the constraints defined in Implementation 3.2.2: Define and Independently Enforce Deterministic Operational Constraints, when a constraint cannot be evaluated (for example, because an input it depends on is degraded or missing), when an AI action is refused under Implementation 5.2.2: Action-Level, Context-Aware Authorization Policies, when the AI system becomes unavailable or degraded, or when the safety wrapper itself fails. In that last case, actions issued by the SI system should stop taking effect and control should pass to the fail-safe state, so that losing the safety wrapper removes the SI system’s authority to act rather than the limits on it.

These fail-safe states should incorporate clear protocols for tracking algorithmic state consistency during failover and re-commissioning cycles. Recovery logic should explicitly dictate whether an overridden AI agent resumes operations by synchronizing with its last active context window, resetting to a validated baseline template state (see also Implementation 5.3.4: Limit the Context Carried Forward Between Steps), or gracefully de-escalating control to a legacy deterministic controller, reducing the chance of sudden uncommanded physical actions from an un-synchronized model state. Where control passes to a fallback controller, that controller should track the live process state continuously while on standby, so that it can take over without a step change in the manipulated variables (known in process control as bumpless transfer). This is the automated counterpart of the State-at-Handoff summary in Implementation 11.2.3: Human Factors and Cognitive Transition Protocols for Control Handoffs. For example: If an AI system commands a valve to be opened while another incompatible valve is also open, the system might fall back onto a less optimal, but known-safe independent deterministic controller to determine, for the current plant state, which valve has precedence.

If a device loses communication with its AI-based controller, it might default to its fail-safe state and broadcast an alert, rather than executing a possibly corrupted last AI-issued command. Note that a ‘fail-safe state’ does not necessarily mean simply de-energizing or shutting down a system, which can introduce secondary hazards. In robotics, for example, a dynamically balancing robot such as a bipedal humanoid needs power to remain standing, so an emergency shutdown can create greater danger from a fall. Fail-safe logic should define deterministic, application-appropriate states, such as holding last-known-safe setpoints, reverting to hard-coded conservative baselines, or reverting control to legacy independent deterministic controllers. Reverting to a legacy controller is available only where that controller has been kept in service, maintained, and tested alongside the SI system (see Task 3.6 and Task 11.2). Where an AI action is refused part-way through a sequence, the fail-safe state should account for the steps already executed, since stopping at the refused step can leave the process in a state nobody designed for. For example, if an AI agent changing over pumps is refused authorization to start the standby pump after it has already stopped the duty pump, the fallback might restart the duty pump or hand the changeover to a deterministic controller, rather than leaving both pumps stopped. Review fail-safe states and fallback behavior under the organization’s existing hazard analysis or functional safety processes, since a fallback that has not been reviewed can itself trigger a cascading failure. For each fallback state from which SI-enabled operation may resume, define the exit conditions and the role, or pre-authorized automated transition, that permits the return. Where the fallback may have been triggered by interference or unreliable inputs, an apparently normal reading or elapsed time alone should not restore the SI system’s prior authority; the return should require the authorization described in Implementation 5.2.2: Action-Level, Context-Aware Authorization Policies and, after an outage, the checks in Task 11.4: Establish System Integrity Re-Validation and Re-Commissioning Protocols. This Implementation should be aligned with those of Practice 4: Define Procedures for Emergency Avoidance Override, Recovery, and Situational Awareness so that immediate-term automated fail-safe and fallback policies are visible to, and align with, subsequent human intervention. Where a fallback holds the last known-safe value, define how long that value can be relied on as process conditions change, and the fallback or escalation that applies once that period ends.

Making the process safe is the first concern, but an abrupt stop or forced shutdown can also leave the system insecure. Cleanup that would normally run can be skipped, leaving sessions, credentials or temporary state in place, interfaces open, or protections not restored on restart. The same class of problem is well documented in conventional software. In one recent example, which was not an attack on an SI system but shows the mechanism, a widely used web platform could be made to abort a request in a way that skipped its normal cleanup, and an attacker could then run their own code (see CVE-2026-109618). An SI system that is stopped or overridden abruptly may be exposed to the same kind of failure. Where this is a risk, define the security actions that accompany a stop, such as revoking the SI system’s sessions and credentials and closing its interfaces, and check on restart that they took effect. Whether these actions run alongside the stop, or the stop waits for some of them to complete, is for the organization to decide, within any regulatory or contractual obligations, weighing the hazard of a delayed stop against the exposure an unclean stop would leave.

Decisions for the Organization:

  • Which fail-safe state applies to each failure condition, including failure of the safety wrapper itself?
  • Which role, or which pre-authorized automated transition, permits the return from each fallback state?
  • How long can a held last-known-safe value be relied on?
  • Which security actions accompany a stop or forced shutdown, and does the stop wait for any of them?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control SI-17, Fail-Safe Procedures, pairs organization-defined failure conditions with fail-safe procedures. Its discussion gives loss of communications between critical components as a failure condition and alerting operators with instructions as a procedure, which is this Implementation’s lost-communication example, and lists subsequent steps ranging from doing nothing or reestablishing system settings to shutting down processes, which supports the point that a fail-safe state need not mean shutting down.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Appendix F.7.6, the OT discussion of CP-10, System Recovery and Reconstitution, addresses whether state variables are restored to initial values or to those before the disruption. Under SC-24, Fail in Known State (Appendix F.7.17), the choice of failure mode may itself disrupt the physical process, with valves failing closed and affecting cooling as the example.
  • Working Document Preliminary Report, October 2026, from the National Security Commission on Robotics for Advanced Manufacturing, a commission initiated by the Special Competitive Studies Project. Under Finding 6, it notes that robots working around people are typically programmed to slow near people and freeze on contact. It also notes that not all form factors can simply shut off, since a dynamically balancing robot such as a bipedal humanoid needs power to remain standing. This is a robotics example of a fail-safe state that is not a shutdown.
  • Incident Report CVE-2026-109618, RCE via OOM corruption, published October 21, 2026, by the PHP project. Says PHP aborts request handling on out-of-memory errors in a way that can “leave request memory in an uninitialized state”, which “The subsequent request cleanup procedure may read or branch on”, leading to remote code execution. A companion record, CVE-2026-109619, describes global state that “may not be correctly reset” and is later read by subsequent requests. Neither was an attack on an SI system; both are cited as examples of the mechanism by which an abrupt stop or incomplete reset can leave a system insecure.
  • Commentary Understanding PHP2Shell: Everything You Need to Know, October 22, 2026, from the Akamai Security Intelligence Group. On CVE-2026-109618, it says the out-of-memory condition “forces PHP to abort execution in unexpected way, so normal cleanup can be bypassed, leaving uninitialized memory vulnerable to malicious overwrite and execution”; not an attack on an SI system, but an example of the mechanism by which a forced stop can leave a system insecure.
