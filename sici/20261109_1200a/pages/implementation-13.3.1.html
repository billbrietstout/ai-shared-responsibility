Implementation 13.3.1: Capture Volatile State Before Teardown

Capturing state that exists only while a system runs helps an organization understand what went wrong after the system is gone. Where retirement follows an incident or a suspected failure, capture working memory, in-flight state and intermediate reasoning artifacts before the execution environment is destroyed. For an SI system, this can include the contents of agent memory, conversation history, and the state of a retrieval index or vector database as it stood at the time. Some containment steps, such as resetting memory or purging conversation history, destroy this state. At a planned retirement, capture may still be worthwhile where a problem could surface only after the system is gone, such as a question about its past decisions. Weigh this against the cost of capture and against any obligation to purge sensitive data at retirement. Record the decision either way. Durable logs and stored records are addressed under Practice 10: Implement Multi-Tiered SI System Logging and Audit Capabilities. This Implementation concerns the state that exists only while the system is running and that teardown destroys permanently. What is kept alongside durable records so that they remain interpretable once the system is gone is considered under Task 10.1: Define Decision-Level Logging and Metadata Retention Policies. This step should precede teardown and resource reclamation, because those actions can make the state unrecoverable. Where the system is suspected of causing harm, its authority and reach can be withdrawn first under Task 13.2: Withdraw All Authority and Confirm the Result, leaving it running long enough for the capture (see the Accountable versus Safe tension in Task 13.3: Preserve What Is Needed and Hand Over What Depended on the System). Where immediate containment rules out capture, follow the pre-established safety response and record what could not be preserved. Some isolation steps, such as disconnecting the system from a network, can themselves destroy volatile state, so the criteria for capture and its order relative to isolation can be decided in advance. Where feasible, capture state with tools independent of the SI system rather than by asking the system to report it, since a compromised system can return false information to the tools that query it. Captured state is itself a record and may hold sensitive or personal material: assign it an accountable owner, access restrictions, a retention basis and period, and a disposition event, as for other SI artifacts governed under Practice 7: Manage Internal SI Supply Chain and Data Provenance. Captured state may be readable only with the software and configuration of the system being retired, so retain or record what is needed to interpret it.

Where an investigation is possible, collect the most volatile state first, compute a hash of each capture so that its integrity can later be shown, and record its chain of custody. The state to capture can also include current adaptive parameters or thresholds where they may differ from those documented, the prompt and configuration versions active at the time, and logs held with short retention by a supplier.

Decisions for the Organization:

  • Is volatile state captured at planned retirements as well as after an incident or suspected failure?
  • Is capture pre-authorized, and does it come before or after isolation? (see the Accountable versus Safe tension in Task 13.3: Preserve What Is Needed and Hand Over What Depended on the System)
  • Who owns captured state, and what are its access restrictions, retention basis and disposition?

References:

  • Guidance NIST SP 800-61r3, Incident Response Recommendations and Considerations for Cybersecurity Risk Management, April 2025, from NIST. In Table 3, recommendation R1 under RS.AN-07 is to collect and retain incident evidence in accordance with evidence preservation procedures and data retention policies, considering the cost of retaining both the data and the hardware and software needed to access it in the future. This bears on keeping captured state readable after the system that produced it is gone.
  • Guidance AI Incident Response Framework, Workstream 2: Preparing Defenders for a Changing Cybersecurity Landscape, version 1.0, 27 October 2025, from the Coalition for Secure AI, an OASIS Open Project. Section 3.3.3 asks for containment to be implemented without destroying evidence, and lists forensic copies before containment and vector database state preservation as evidence preservation steps. It also notes that containment for an SI system with memory can mean resetting memory and purging conversation history. This bears on the order of capture and containment in this Implementation.
  • Guidance NIST SP 800-86, Guide to Integrating Forensic Techniques into Incident Response, August 2006, from NIST. Section 5.2.1, Collecting Volatile OS Data, notes that volatile data can be collected only from a live system, that powering off or even disconnecting a system from a network can end the opportunity to collect it, and that the criteria for deciding whether to preserve it should be documented in advance. Section 5.2.1.1 warns that a fully compromised system can return false data to the tools that query it. Written for operating systems, it bears on the order and the means of capture in this Implementation.
