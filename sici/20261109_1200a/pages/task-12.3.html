Task 12.3: Manage Operational Continuity and Resilience for Generated Artifacts

Establish safeguards to protect system availability and safety throughout the lifecycle of AI-generated logic. This includes utilizing isolated testing environments, maintaining strict version control for machine-authored artifacts, and maintaining human-verified ‘known-good’ configurations for rapid rollback and recovery. Where the same generated artifact is to be deployed across several units or sites, a staged deployment that starts with one unit or a less critical segment can limit the spread of a defect that the artifact carries (see NIST SP 800-40r4). Engineers should be able to read, maintain and correct machine-authored logic without the generating SI system, and rollback should not depend on that system being available. Making it visible to operators which recent changes were machine-generated can help them link unexpected behavior to a likely cause. Latent defects are not always accidental. A poisoned code-suggestion model can be made to suggest insecure code (see NIST AI 100-2e2025).

Main Trustworthiness Contributions:

  • Resilient: Contributes a strict version history of AI-generated operational logic and a human-verified known-good configuration or procedure kept available as a fallback, so that a failing artifact can be rolled back rather than repaired under pressure. This Task does not cover sustained operation without AI support, which Task 11.2: Define Manual and Alternative Operating Procedures for Long-Term Mission Continuity covers.
  • Reliable: Contributes isolated testing of generated configurations and code before deployment where feasible, and monitoring of systems running on them for configuration drift and latent errors that initial validation did not reveal. This Task does not cover monitoring the behavior of the generating AI system itself, which Task 3.4: Monitor for Anomalous SI Behavior covers.

Trustworthiness Side Effects to Consider:

  • Secure: Rolling back to a known-good version can reintroduce a defect, including a security vulnerability, that a later version corrected. Implementation 12.3.2: Version Control and Rollback Procedures records why each version replaced the one before it, so that this can be checked before a rollback.

Related AI RMF Subcategories Include:

  • MANAGE 4.1 (on post-deployment risk management): This Task covers monitoring for latent failures in systems running on AI-generated configurations, with version control and known-good rollback as the recovery and change mechanism; it does not cover incident response once a failure has occurred. For that, see for example Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures.
  • MEASURE 2.3 (on ensuring realistic measurement): This Task covers testing of generated configurations and code in a digital twin or isolated simulation before production, where feasible; it does not set out the fidelity such environments need or the limits of what they can replicate. For that, see for example Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior.

Decisions for the Organization:

  • Which generated artifacts are deployed in stages, and which unit, site or segment goes first?
  • What applies where no human-verified known-good version exists for a generated artifact, for example for a new function?

References:

  • Guidance NIST SP 800-40r4, Guide to Enterprise Patch Management Planning: Preventive Maintenance for Technology, April 2022, from NIST. Section 3.5.1, Maintenance Plans for Scenario 1, Routine Patching, suggests phased deployments in which a small subset of assets receive a patch first and act as canaries for identifying issues before the rollout expands. Section 3.5.2 suggests the same approach, on an accelerated schedule, for emergency patching. Written for patches, it carries over to staging a generated artifact across units or sites.
  • Guidance NIST AI 100-2e2025, Adversarial Machine Learning: A Taxonomy and Terminology of Attacks and Mitigations, March 2025, from NIST. Section 3.2.1, Data Poisoning Attacks, notes that poisoning the data used to train a generative AI system can lead to a range of bad outcomes, such as code suggestion models that intentionally suggest insecure code. This bears on this Task’s monitoring for latent errors, some of which may have been introduced deliberately.
