Implementation 7.3.2: Automate Policy-as-Code

Translate safety and operational policies into automated, machine-readable logic rules embedded directly within the deployment workflow (often referred to as Policy-as-Code). Inference requests that possess mission impact should be logged with their full context, including version identifiers of safety filters and any triggered rules (e.g., “Blocked: Safety Boundary Violation”). All changes to underlying safety logic should require cryptographic signatures, appropriate approval oversight, and automated regression testing (informed by Practice 2: Define SI Robustness, Resilience, and Quality of Service Expectations) to help ensure updates do not inadvertently degrade system availability. Include in the regression tests cases that the rules are meant to block, drawn from the failure modes mapped under Implementation 2.3.2: Targeted Failure Mode Mapping, so that a change that weakens a safety boundary is detected as well as one that blocks legitimate requests. Record for each rule the policy, regulation or other requirement it implements, so that a change to that source can be traced to the rules it affects, and a triggered rule can be traced back to its source. The rule set, and logs that name each triggered rule, show exactly what is blocked and why. An attacker could use them to shape requests that fall just outside every rule. Protecting them is a matter for the organization’s existing information classification and handling practice.

References:

  • Standard ISO/IEC/IEEE 15288:2023, Systems and software engineering: system life cycle processes, published jointly by ISO, IEC and IEEE. Clause 6.4.2.3, in its task to maintain traceability of stakeholder needs and requirements, notes that bi-directional traceability is maintained through the life cycle between the needs and requirements and their stakeholders and sources. This is the traceability this Implementation asks for between each machine-readable rule and the requirement it implements.
  • Guidance OWASP Top 10 for Agentic Applications, Version 2026, December 2025, from the Agentic Security Initiative of the OWASP Gen AI Security Project, a volunteer community project of the Open Worldwide Application Security Project. Entry ASI08, Cascading Failures, includes among its mitigations validating every high-impact tool invocation against a policy-as-code rule before executing it, and separating planning from execution through an external policy engine. This is a runtime form of the machine-readable safety rules this Implementation asks for.
