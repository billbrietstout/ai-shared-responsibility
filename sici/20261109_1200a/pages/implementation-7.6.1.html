Implementation 7.6.1: Internal Dependency Mapping (Orphan System Prevention)

Mapping what depends on an SI component before it is turned off helps the organization retire it without leaving dependent systems broken. Before decommissioning an internal AI agent, system, tool, model or API, organizations should audit the internal supply chain to identify, as completely as practical, the downstream IT, OT, or ICS systems that rely on its outputs. Build the map from observation as well as documentation, for example from API gateway logs, use of the component’s credentials and network flow records. These can reveal callers that were never registered. The resulting map shows which systems would fail if a component stopped responding, which an attacker could use to choose a target for disruption. Protecting it is a matter for the organization’s existing information classification and handling practice, as with the mapping under Implementation 3.5.1: Map Direct Functional and Algorithmic Dependencies. A deprecation period in which calls are still served but logged and flagged can surface remaining dependents before the component is turned off. Establish strict “deprecation timelines” and notifications to help ensure dependent systems are safely refactored, or reverted to deterministic fallbacks where these exist or can be prepared, before the model is turned off. Where neither is possible in time, Implementation 7.6.3: Legacy Logic Vulnerability Management applies. The process of mapping dependencies is common to Implementation 3.5.1: Map Direct Functional and Algorithmic Dependencies and, for shared infrastructure, Implementation 3.5.2: Identify Indirect Shared Infrastructure and Collateral Damage Exposure. If that mapping has already been performed and kept current, much of the groundwork for decommissioning will already be in place. Implementation 13.3.3: Determine and Record What Happens to Everything that Depended on the System requires that a decision is recorded for each dependent identified here, including where that decision is to make no provision.

Decisions for the Organization:

  • How long is the deprecation period, and what happens to dependents not refactored by its end?

References:

  • Standard ISO/IEC/IEEE 15288:2023, Systems and software engineering: system life cycle processes, published jointly by ISO, IEC and IEEE. Clause 6.4.14, the disposal process, notes under its task to deactivate a system or system element that interfaces to other systems are considered, and that when a system is modified for upgrades only the impacted system elements are deactivated and removed. This is the systems-engineering form of the dependency audit this Implementation asks for before an internal SI component is turned off.
  • Guidance NIST IR 8179, Criticality Analysis Process Model: Prioritizing Systems and Components, April 2018, from NIST. Sub-process B.2 asks that interactions between activities or processes be examined to determine which processes rely on the outputs of others, and that the result be mapped, including what must be completed before another process can begin. This is a structured method for identifying the downstream systems that rely on an SI component’s outputs, as this Implementation asks.
