Task 11.4: Establish System Integrity Re-Validation and Re-Commissioning Protocols

Agreeing in advance what an SI system must demonstrate before a return helps an organization judge when the system is ready, and withstand pressure to restore automated service too early. Define the technical benchmarks and safety tests a system should pass before it is allowed to transition from manual mode back to automated operations. Organizations with established return-to-service checks for equipment can build on them for an SI system. Re-validation testing pathways should explicitly reference and execute the TEVV protocols established in Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle. This helps ensure that “turning the AI back on” does not introduce new cascading risks and is supported by verifiable, auditable evidence of system health. During manual operation, personnel may have replaced equipment, adjusted setpoints by hand or recalibrated instruments. The benchmarks should include reconciling the SI system’s inputs, stored state and any retained context with the current state of the process before automated operation resumes. Where the SI system was updated or replaced during the outage, the baselines and the records from before the outage may no longer describe it (see Task 10.1: Define Decision-Level Logging and Metadata Retention Policies). Where the protocol cannot be completed, continued manual or degraded operation where it can be sustained (see Task 11.3: Pre-Allocate Operational Resources for Alternative Service Delivery), or a controlled shutdown under Implementation 11.2.4: Unplanned Shutdown and Controlled Isolation Protocols, should be the default rather than a provisional return to automated operation.

Main Trustworthiness Contributions:

  • Safe: Contributes the gate before automated operation resumes: a signed-off checklist confirming the root cause of the outage has been addressed or, where it could not be identified, that compensating controls and safety margins are in place (Implementation 11.4.1: Define a Checklist for Validating System Safety Before Re-Engaging SI Control), shadow-mode comparison against the manual process, and separate confirmation that independent safety protections respond correctly (Implementation 11.4.2: Implement “Shadow Mode” Validation and Independent Safety Protection Checks for SI Re-Commissioning). This Task does not cover performing the root cause analysis it checks for, which Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures addresses, including Task 8.2: Identify Additional Controls that May Be Required in Scenarios Where Deterministic Root Cause Analysis Is Not Possible for failures whose cause cannot be traced.
  • Valid: Contributes re-establishing fit after an outage by re-running the TEVV protocols and comparing behavior against known baselines, rather than assuming the system that returns is the one that was accepted. This Task does not cover setting those protocols, which Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle covers.

Trustworthiness Tensions to Balance:

  • Resilient versus Safe: Where manual operation is comfortably sustainable, extended shadow-mode validation before re-commissioning costs little. Where manual operation is consuming standby resources and running less efficiently, as Task 11.3: Pre-Allocate Operational Resources for Alternative Service Delivery anticipates, pressure to turn the AI system back on grows while the evidence is still incomplete. One way to balance this is the one this Task takes: setting the benchmarks before the outage, so that the decision is made against them rather than under pressure; others include restoring automated control incrementally, one sub-system at a time.

Related AI RMF Subcategories Include:

  • MANAGE 2.3 (on responding to emerging risks): This Task covers the recovery end of that response, in checks that the cause of an outage has been addressed before automated operation resumes; it does not cover identifying or investigating the risk. For those, see for example Task 3.4: Monitor for Anomalous SI Behavior for detection and Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures for investigation.
  • MEASURE 2.5 (on measuring validity and reliability): This Task covers a renewed demonstration of validity before re-commissioning, by re-executing TEVV and comparing behavior against known baselines; it does not cover documenting the limits of generalizability that MEASURE 2.5 also names, or establish the baselines it compares against. For the baselines, see Implementation 2.3.1: Baseline SI System Performance.
  • MEASURE 2.6 (on measuring safety): This Task covers confirmation that independent safety protections respond correctly before the AI system resumes live authority; it does not cover setting the residual risk tolerance against which acceptable safety is judged. For that, see for example Implementation 3.1.3: Define Acceptable Risk Thresholds and Associated Control Responses.

Decisions for the Organization:

  • Which benchmarks must be met before automated operation resumes, and who decides that they are met? (see the Resilient versus Safe tension)
  • What is done, and who decides, if manual operation cannot be sustained until the benchmarks are met? (Implementation 3.9.6: Keep a Record of Design Decisions and Accepted Risks)

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control CP-10, System Recovery and Reconstitution, recovers and reconstitutes a system to a known state, and its discussion includes assessment of fully restored capabilities, reestablishment of continuous monitoring, and reauthorization where required, which parallels the checks this Task calls for before an AI system resumes automated operation.
  • Guidance NIST SP 800-160v2r1, Developing Cyber-Resilient Systems: A Systems Security Engineering Approach, from NIST. Table 2 notes, under the Recover goal, that restoration can be incremental and that a key challenge is determining how much trust can be placed in restored functions and data as restoration progresses, and Table D-1 lists heightening protections during reconstitution and determining the trustworthiness of restored or reconstructed resources among the Reconstitute sub-objectives, which is the judgment this Task asks to be made against defined benchmarks before AI control resumes.
