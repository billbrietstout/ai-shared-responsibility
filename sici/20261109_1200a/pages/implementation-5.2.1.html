Implementation 5.2.1: Map and Document SI Agent Access to Operational and Data Assets

Create and maintain a record of the systems, data sources, and physical assets each AI agent can reach, updated whenever an agent’s role or deployment changes. This map is the prerequisite for enforcing least privilege in Task 5.3: Implement Principles of Least Agency and Least Privilege for SI Entities and for scoping what a compromised or malfunctioning agent could actually affect. Include the tools each agent can invoke, the identity under which each tool connects to downstream systems, and the permissions that identity holds. A tool can reach downstream systems with broader rights than the agent was meant to have, for example by connecting with a generic high-privileged account. Record the upstream and downstream resources and service accounts that the agent’s workflow uses, so that the map also shows what the agent can affect indirectly. Tools trialed during development and later replaced should be removed rather than left available to the agent. Record the actions each agent may take on each asset, such as read, write, command or approve, and not only whether it can reach the asset. Derive the record from the permissions actually configured in identity providers, gateways and tools, and compare it with the intended design, so that access granted outside the design is visible. Mark access that can change a physical process, alter safety-relevant data or take an action that cannot be reversed, so that it can be prioritized under Task 5.3 and Implementation 5.2.3.

Decisions for the Organization:

  • Which access is marked as able to change a physical process, alter safety-relevant data or take an action that cannot be reversed?
  • Who maintains the access map, and with what effort is it kept current as agents, tools, and deployments change?

References:

  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM03:2026, Excessive Agency, lists among its common examples a tool trialed during development that remains available to the agent after being replaced, and a tool that connects to downstream systems with a generic high-privileged identity. Both bear on recording the tools each agent can invoke and the identities those tools use.
  • Guidance NIST SP 800-207, Zero Trust Architecture, from NIST. Section 7.3.4, Formulating Policies for the ZTA Candidate, asks that once a workflow is identified, the upstream resources, downstream resources and entities such as service accounts that it uses or affects are identified. This bears on mapping what an agent’s workflow can reach indirectly as well as directly.
