Task 2.1: Establish SI Usage Thresholds and Rate Control Mechanisms

Limits on how much and how fast an SI system can act help keep unexpected behavior from overwhelming the equipment, systems, and people around it. Define and implement technical constraints on the volume, frequency, and scope of SI-driven actions, communications, and resource usage, particularly where there are physical and safety limitations or constrained resources.

This Task reduces the potential for rapid, automated system instability and resource bottlenecks by helping ensure that SI interactions remain within predefined operational tolerances and do not overwhelm upstream or downstream legacy systems. Record the operational basis for each threshold, such as the equipment rating or process constraint it reflects, so that it can be reviewed when the process, the equipment or the SI system changes. Rate limiting and throttling are established practice for networks, application interfaces, and alarm systems, and this Task applies them to what an SI system can do.

Main Trustworthiness Contributions:

  • Resilient: Contributes a ceiling on how fast a departure can propagate, so that an SI system behaving unexpectedly consumes a bounded amount of resource, control authority and operator attention before the wider system falls back to its fail-safe state or other fallback behavior (Implementation 2.1.1: Implement Baseline Rate Limiting). This Task does not cover the independent mechanism that acts once that ceiling is reached. For that, see Task 2.2: Establish Requirements for Redundancy in SI-Driven Functions, and for the fail-safe state or other fallback behavior the wider system falls back to, Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior.
  • Safe: Contributes limits placed where SI activity meets physical and resource constraints, holding the volume, frequency and scope of automated action within what the surrounding equipment and legacy systems were built to absorb. This Task does not cover defining the operating boundary that an individual command should respect, which Implementation 3.2.2: Define and Independently Enforce Deterministic Operational Constraints covers.

Trustworthiness Side Effects to Consider:

  • Transparent: An SI system held at a limit continues to operate while its activity is being constrained, so the constraint is a fact about the deployment that should be recorded and notified rather than inferred. Implementation 2.1.1: Implement Baseline Rate Limiting directs notification of limit events, and Practice 10: Implement Multi-Tiered SI System Logging and Audit Capabilities covers retention of the record.
  • Secure: The recorded thresholds and their basis show how much activity the SI system may carry out before it is limited, and what happens when a limit is reached. An attacker could use them to keep malicious activity just under a limit, or to trip a limit on purpose and force the fallback. Protecting the threshold records is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Safe versus Safe: Where the SI system’s demand is steady, a fixed ceiling holds automated activity inside what the surrounding equipment can absorb. Where a fast-moving abnormal condition calls for a higher volume of valid commands, such as a rapid pressure excursion or a cascading equipment fault, the same ceiling can suppress correct action at the moment it matters most. Options include Implementation 2.1.2: Develop Process-Informed Guardrails, which sets the permitted rate from the state of the process rather than as a single fixed value across all operating conditions. Where prepared in advance, other options include raising the ceiling for a declared abnormal condition, or treating a limit reached during an excursion as a trigger for the fallback in Task 2.2: Establish Requirements for Redundancy in SI-Driven Functions rather than as a cap held in place. Each carries its own considerations, such as who may declare the abnormal condition and whether the fallback is ready to take over.

Related AI RMF Subcategories Include:

  • MAP 4.2 (on establishing risk controls for SI system components): This Task covers rate limits, process-informed guardrails and throttles as the internal controls placed around the SI component itself; it does not cover the independent mechanism that acts once those controls are exceeded. For that, see for example Task 2.2: Establish Requirements for Redundancy in SI-Driven Functions.
  • MEASURE 2.4 (on monitoring deployed SI systems): This Task covers the automatic response to production monitoring, throttling the SI system when its behavior departs from expected patterns; it does not cover defining the detection regime that recognizes the departure. For that, see for example Task 3.4: Monitor for Anomalous SI Behavior.

Decisions for the Organization:

  • How is each rate ceiling set, and what headroom is kept for abnormal conditions that call for a higher volume of valid commands? (see the Safe versus Safe tension in Task 2.1: Establish SI Usage Thresholds and Rate Control Mechanisms)
  • Who may change a rate limit, including during an abnormal condition, and how is the change recorded?
