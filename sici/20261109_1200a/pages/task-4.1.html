Task 4.1: Establish “Break-Glass” Intervention Procedures

Define procedures by which authorized, trained personnel can safely override SI-driven actions in a timely manner during an emergency situation, similar to how a “break-glass” button provides the ability to override access control in the event of a fire or other emergency. Note that in many applications, simply disabling the SI system, for example with a kill switch that cuts it off without a defined handover, can leave the overall system in an unsafe state. This Task should establish overall procedures for personnel to obtain appropriate situational awareness (Task 4.2: Ensure that Personnel Are Able to Gain and Maintain Situational Awareness), and decide on the appropriate action to take. These should align with the fallback behaviors in Task 3.2: Implement Independent Guardrails for SI Outputs. Where the organization already maintains emergency operating procedures, consider incorporating these procedures into them rather than keeping a separate document. The procedures should be exercised as described in Implementation 4.1.3: Regularly Practice and Evaluate Intervention Processes.

Main Trustworthiness Contributions:

  • Safe: Contributes the executable override path: intercept points that are reliably implemented (Implementation 4.1.1: Ensure that SI Systems Can Be Reliably Overridden), and a ladder of tiers so that intervention need not be all or nothing. This Task does not cover the fallback states entered on override, which Task 3.2: Implement Independent Guardrails for SI Outputs covers.
  • Accountable: Contributes authorization allocated in advance: which tier a role may invoke, where a second authorizer is required, and who decides when the cause of an anomaly is not yet clear. This Task does not cover the ability to enforce that decision, which Task 3.9: Assess and Document Organizational Readiness for Each SI-Enabled Capability covers.

Trustworthiness Side Effects to Consider:

  • Reliable: Exercising the override path is itself an operational action, and rehearsal on a production system can trip or suspend the function it protects. Implementation 4.1.3: Regularly Practice and Evaluate Intervention Processes directs that testing to the environments categorized in Implementation 1.3.2: Categorization of Testing Environments.
  • Secure: The intervention procedures, tier definitions, and after action reports from exercises (Implementation 4.1.3: Regularly Practice and Evaluate Intervention Processes) show which actions stop or bypass the SI system, who may invoke them, what state each leaves the process in, and where the procedures fell short. An attacker could use them to impersonate an authorized responder, to trigger a tier that leaves the process unsafe, or to time an attack for when intervention is slow. Protecting them is a matter for the organization’s existing information classification and handling practice, while keeping what external emergency responders need within their reach. Implementation 4.1.2: Establish Tiered Intervention Procedures, Training, and Authorization limits who may invoke each tier.

Trustworthiness Tensions to Balance:

  • Safe versus Secure, Accountable and Safe itself: Where intervening personnel are pre-credentialed and the tier has been rehearsed, authorization and speed move together. Where the intervening party is an external responder arriving unannounced, each authorization step lengthens the emergency that the break-glass path exists to shorten. The same step is what confirms that the person invoking a tier is entitled and trained to use it, whether the concern is a malicious actor or a well-meaning responder choosing a tier that leaves the process unsafe.

Related AI RMF Subcategories Include:

  • MANAGE 2.4 (on decommissioning or superseding AI systems): This Task covers how authorized personnel disengage or override an AI system at the moment its behavior becomes unsafe, and the tiers of authority for doing so; it does not cover the situational picture on which that decision rests. For that, see for example Task 4.2: Ensure that Personnel Are Able to Gain and Maintain Situational Awareness.
  • MAP 3.5 (on establishing human oversight processes): This Task defines the intervention procedure itself and assesses it through tabletop exercise under adversarial scenarios; it does not cover determining which operational contexts admit real-time human oversight at all. For that, see for example Task 4.5: Define Operational Regimes for Human-on-the-Loop and Human-Out-of-the-Loop Operation.
  • MAP 3.4 (on defining operator proficiency): This Task sets tiered training, authorization and access control for the personnel permitted to intervene, including external emergency responders; it does not cover the manual operating skills that erode through routine reliance on the AI. For those, see for example Task 3.6: Mitigate Automation Complacency and Skills Degradation.
  • MANAGE 2.3 (on responding to emerging risks): This Task pre-establishes decision authority for anomalies whose underlying cause is not yet clear, so that a responder is not delayed during a machine-speed event; it does not cover the investigation that afterward determines what the risk was. For that, see for example Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures.

Decisions for the Organization:

  • Are the intervention procedures folded into existing emergency operating procedures or kept separate?
  • How many authorization steps does each tier carry, given who is likely to invoke it? (see the Safe versus Secure, Accountable and Safe itself tension)
  • Who maintains the intervention procedures, training, and authorizations, including outside normal hours, and what resources does that need?
  • What should personnel do when the intended tier or override mechanism is unavailable?

References:

  • Working Document National Security Commission on Robotics for Advanced Manufacturing, Preliminary Report, October 2026, from the Commission, an initiative of the not-for-profit Special Competitive Studies Project. The section Safety, Performance, and Liability Frameworks Are Lagging Emerging Robot Capabilities notes that not all robots can simply shut off when safety is at risk: a bipedal humanoid needs power to remain standing, and an emergency shutdown can create greater danger from a falling robot. This illustrates this Task’s point about disabling an SI system without a defined handover.
