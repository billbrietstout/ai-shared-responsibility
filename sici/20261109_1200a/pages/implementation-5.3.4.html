Implementation 5.3.4: Limit the Context Carried Forward Between Steps

For agentic and multi-turn AI systems, define what context each step, session and delegated agent receives, including conversation history, retrieved material, tool outputs and stored memory, and pass forward only what the next step requires. This is the agentic, runtime case of selecting the inputs an AI system receives (Implementation 7.2.4: Select and Prepare the Inputs Each SI System Receives). Material carried forward can be poisoned, can leak through later outputs or tool calls, can steer later decisions, and needs to be recorded if a decision is to be reconstructed (Implementation 8.1.5: Multi-Agent Cascade Reconstruction Capabilities). Context a step does not need adds those exposures, and can increase inference cost, without adding capability. Indeed, reducing context by filtering out unnecessary and distracting information can improve capability and accuracy, although it does introduce risk associated with important context being incorrectly filtered out. A tool call or output that would be permitted in isolation can still disclose sensitive information accumulated earlier in the interaction, so privacy and data-handling checks at the point of a tool call or output should consider the context the SI system carries, not only the request itself.

Approaches include:

  • Keeping the contexts of different users, tasks and domains separate.
  • Expiring material that has not been verified rather than retaining it indefinitely.
  • Not feeding an agent’s own outputs back into memory it treats as trusted.
  • Treating material received from another agent with the same scrutiny as external input, since arriving from inside the system does not make it more reliable.
  • Resetting long-running agents to a known baseline state at defined points, one of the recovery options in Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior.
  • When delegating under Implementation 5.3.3: Separate Privilege via Encapsulated Downstream Agents and Tools, passing the request and its scope rather than the delegating agent’s full context.

Where a claim passes from one step or agent to the next, carry its uncertainty, qualifications and source with it, since a claim that one agent marked as uncertain or inferred can otherwise reach a later step, or a person, as if it were established. Too little context can degrade decisions, so the aim is the context the task needs, which can be tested under Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle, rather than the least possible. Credentials can be kept out of the context altogether, with tools obtaining them from a secrets store or attaching them at the point of use, so that they do not appear where later steps or outputs could expose them. Safety-relevant operating constraints, such as equipment that is under clearance or out of service, can be passed to each step explicitly rather than left for the SI system to recall from earlier history, and testing can confirm that limits on context do not drop them.

Limiting the context carried forward is akin to a practice familiar in control engineering and automation, where the feedback signal reaching a controller is often filtered to remove noise and spurious signals that could otherwise mislead it, but where filtering too heavily introduces risks associated with delaying or distorting the controller’s response to real changes.

Decisions for the Organization:

  • What context does each step, session and delegated agent receive, and how is that tested? (see the Accurate versus Secure, Privacy-Enhanced and Accurate itself tension in Task 5.3: Implement Principles of Least Agency and Least Privilege for SI Entities)

References:

  • Guidance OWASP Top 10 for Agentic Applications, Version 2026, December 2025, from the Agentic Security Initiative of the OWASP Gen AI Security Project, a volunteer community project of the Open Worldwide Application Security Project. Entry ASI06, Memory and Context Poisoning, includes among its mitigations isolating user sessions and domain contexts, enforcing context-aware access per task and minimizing retention by data sensitivity, preventing automatic re-ingestion of an agent’s own outputs into trusted memory, and expiring unverified memory to limit how long poisoned material persists.
  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, August 4, 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM02:2026, Sensitive Information Disclosure, lists among the foundational mitigations for every deployment to minimize context, sending only task-required fields to external providers and disabling automatic context unless it is justified. LLM08:2026, Hidden Context Exposure, asks that credentials, secrets and security-critical configuration not be embedded in system prompts or hidden context, and that such information be externalized to systems that the model does not directly access.
  • Guidance NIST SP 800-160v1r1, Engineering Trustworthy Secure Systems, from NIST. Principle E.15, Least Persistence, states that system elements and other resources are available, accessible and able to fulfill their design intent only for the time for which they are needed, and its note applies this to data and information remaining present when not required, which reduces the opportunity for their inadvertent or unauthorized use or modification.
