Appendix C: Use Cases and Operational Scenarios

This appendix presents illustrative use cases and operational scenarios, and shows how Practices, Tasks and Implementations in this profile apply to them. Unlike the scenarios in Appendix B, these are developed from use cases rather than inspired by historical incidents. Each scenario is presented in the same form:

  • Scenario. The situation, in the sector’s own terms.
  • The question that matters. The decision the scenario turns on.
  • Risks to consider. The specific conditions that change the answer.
  • How this profile applies. The relevant items and what each contributes.
  • What the record should show. What should be reconstructable afterward.

The scenarios are not exhaustive, and the items listed are not the only ones that may apply.

To the Reviewer: We welcome further use cases and operational scenarios, particularly ones specific to sectors not yet represented here. Short descriptions are useful; we can help develop them into this form.

C.1 Healthcare: Authorized Access versus Authorized Action

Critical Infrastructure Sector: Healthcare and Public Health. Contributed by a member of the community of interest.

Scenario. A health system approves an AI tool for use in a defined part of a clinical workflow. To do that work, the tool has legitimate access to the electronic health record (EHR). A clinician allows the tool to assist with that part of the workflow. Later, the tool attempts an action that its access makes technically possible but that falls outside the scope the clinician allowed.

The question that matters. The question is not only whether the tool is authenticated, or whether it is technically able to take the action. It is whether that specific action is authorized at that point in time.

Risks to consider. Access granted for one purpose may outlast or exceed the authority behind it. For example:

  • the clinician’s role may have changed since the authority was granted;
  • the authorization may have expired or been revoked;
  • the workflow may be different from the one that was approved;
  • the action may require a separate human decision that the tool cannot make on the clinician’s behalf.

In each case, an access check alone would allow the action.

How this profile applies.

  • Practice 5: Implement Identity and Access Management (IdAM) for SI Agents, Systems, and Tools is the main Practice. Within it:
  • Task 5.1: Establish Identities and Authentication for SI Entities gives the tool, and each instance of it, an identity distinct from the clinician’s and from other systems. As that Task notes, an identity establishes which entity is acting, not what it is permitted to do.
  • Implementation 5.2.1: Map and Document SI Agent Access to Operational and Data Assets records what the tool can reach in the EHR, which shows how far its access exceeds its approved scope.
  • Implementation 5.2.3: Determine the Appropriate Level of Agent, Asset, and Permission Granularity decides how finely that access is divided. For example, read access to a record may be separated from the ability to enter orders or change a care plan.
  • Implementation 5.2.2: Action-Level, Context-Aware Authorization Policies is the central control. It evaluates each proposed action at the moment of execution against the requesting tool’s identity, its current task scope, operational state and any required human approvals. It also holds that an authenticated session or prior authorization does not grant blanket permission for later actions.
  • Implementation 5.3.2: Task-Bounded and Revocable Agent Authority binds the tool’s authority to a specific task or time window, with automatic expiry and rapid revocation. This addresses authority that has expired, has been revoked, or no longer matches the clinician’s role.
  • Task 3.2: Implement Independent Guardrails for SI Outputs and Implementation 3.2.1: Identify SI Output Intercept Points place the check between the tool’s request and its effect in the EHR, as independent of the tool as practical. As Task 3.2: Implement Independent Guardrails for SI Outputs notes, identity, per-action authorization and decision-level records act on the same path, and organizations may find it useful to check them together.
  • Implementation 3.3.3: Actionable Operator Decision & Escalation Pathways defines the response once the check has been made: allow the action, route it for human review, or stop it, according to the organization’s policy. Where authority cannot be verified, Implementation 5.2.2: Action-Level, Context-Aware Authorization Policies points to Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior.
  • Task 10.1: Define Decision-Level Logging and Metadata Retention Policies and Implementation 10.1.2: Runtime Telemetry and Artifact Tracking provide the record. Implementation 10.1.2: Runtime Telemetry and Artifact Tracking asks that records of what action was taken, and whether it was permitted, be generated where possible by the enforcement layer rather than reported by the tool about itself.
  • Task 5.4: Implement Continuous Monitoring of SI Entities Against Access and Action Boundaries and Expectations reviews access and authorization events over time. This can show a pattern of out-of-scope requests that no single blocked action would reveal.
