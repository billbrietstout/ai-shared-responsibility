Practice 12: Independently Verify SI-Generated Operational Logic and Artifacts Across Their Lifecycle

Establish rigorous, SI-aware validation and verification protocols for SI-generated artifacts, including code, configurations, and procedures, that direct or influence the execution of critical infrastructure operations.

Independent verification helps an organization catch errors in SI-generated code, configurations, and procedures before they direct operations. SI-generated artifacts can be hard to review well. They are often fluent and plausible, they can be produced in volumes that outpace the people available to check them, and their errors tend to be the kind that look correct to a reviewer who does not have deep knowledge of the specific deployment, even one who is a subject matter expert. This Practice supports scrutiny of machine-authored code, configurations, and procedures against formal specifications and tacit institutional knowledge. It helps reduce the chance that ‘plausible but inaccurate’ logic is deployed in high-consequence IT, OT, and ICS environments.

This risk is heightened in applications where vital distinctions between identifiers and concepts don’t follow easily verified rules. For example, incorrectly generated or hallucinated configuration syntax may be easily identified by rule but an incorrectly generated device identifier may be difficult to detect, and may happen to match a real, unrelated device.

Errors are not the only source of such logic: a manipulated retrieval source or an injected prompt can lead an SI system to produce an artifact that looks routine but contains a deliberate weakness (see Task 3.8: Scope and Map the Expanded SI Attack Surface and Risk Surface). When a flaw is found in one generated artifact, the provenance record kept under Implementation 12.1.2: Provenance and Traceability can help locate the other artifacts produced by the same model version, prompt or context, which may share it.

Verification, especially human review, is only as good as the time, expertise, and attention available for it. Where SI systems produce artifacts faster than qualified reviewers can examine them, review can become a signature rather than a check, and the volume of generated artifacts can grow without anyone deciding that it should. Matching the depth of review to consequence (Implementation 12.1.1: Artifact Risk Classification), and planning for the reviewers that this calls for, including when they are unavailable, can help keep verification meaningful. Where that capacity is not available, limiting what is generated, or how far it is relied on, is an alternative to reviewing it less carefully.

Task 12.1: Establish Governance and Accountability for SI-Generated Execution Artifacts assigns each artifact a consequence-based risk tier and an accountable human approver, Task 12.2: Implement Multi-Layered Validation of Machine-Authored Logic combines deterministic testing with expert review, and Task 12.3: Manage Operational Continuity and Resilience for Generated Artifacts keeps human-verified known-good configurations available for rollback and recovery.

Main Trustworthiness Contributions:

  • Valid: Contributes checking of machine-authored code, configurations, and procedures against both written specifications and the unwritten operating norms of the specific facility before they direct operations, so that logic which reads as correct but is wrong is more likely to be caught before anyone or any system relies on it. This Practice does not cover setting the requirements those artifacts are checked against, which Practice 1: Establish Requirements for Success sets out.
  • Accountable: Contributes a named human owner and a defined deployment authority for every machine-authored artifact, with a record tying it to the model version, prompt, and context that produced it, so that no generated artifact enters service on the SI system’s authority alone. This Practice does not cover establishing the wider decision authority those roles sit within, which Practice 3: Define Risks, Policies, and Oversight for Automated, Agentic, and SI Behavior sets out.
  • Resilient: Contributes an appropriately human-verified known-good version of each generated configuration or procedure, held ready so that a failing artifact can be rolled back rather than repaired under pressure. This Practice does not cover sustained operation without SI support, which Practice 11: Maintain SI-Aware Mission Continuity and Disaster Recovery Planning covers.

Trustworthiness Side Effects to Consider:

  • Secure and Privacy-Enhanced: Tracing each artifact to the prompt and context that produced it means retaining those prompts, which may carry sensitive procedures, credentials or personal information about staff, customers or patients. Practice 10: Implement Multi-Tiered SI System Logging and Audit Capabilities sets the access controls, privacy partitioning and tamper evidence for captured records of this kind.
  • Secure: The risk classes, verifier rule sets and recorded facility norms this Practice produces show which artifacts matter most, which constraints are checked automatically and which are not, and where the plant has known weaknesses. An attacker could use them to choose targets or to shape a weakened artifact so that it passes the checks. Protecting them is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Safe and Valid versus Resilient: Where time permits, verifying a new artifact before it is used serves both. Where service must be restored urgently, waiting for full verification of a new artifact can prolong degraded service, while bypassing verification can put an artifact that is wrong for its use into service and introduce a new hazard. Where a previously verified known-good artifact has been kept under Implementation 12.3.2: Version Control and Rollback Procedures, restoring it while the new one completes verification can serve both. A rollback carries its own considerations, such as reintroducing a defect that a later version corrected (see Task 12.3: Manage Operational Continuity and Resilience for Generated Artifacts).

Related AI RMF Subcategories Include:

  • MAP 4.2 (on establishing risk controls for SI system components): This Practice covers the controls applied to code, configurations and procedures an SI system generates, before and after they enter service; it does not cover controls on an SI system’s own outputs at the process boundary. For that, see for example Practice 3: Define Risks, Policies, and Oversight for Automated, Agentic, and SI Behavior.
  • GOVERN 4.1 (on establishing a risk-aware culture): This Practice covers the position that machine-authored logic is unverified until independently checked, however plausible it reads; it does not address operators’ reliance on SI outputs during operation. For that, see for example Practice 9: Provide Role-Based SI Risk Training that Builds Well-Founded Trust.
  • MANAGE 4.1 (on post-deployment risk management): This Practice covers version history, known-good rollback and monitoring for latent failures in SI-generated logic once it is in service; it does not cover the incident response that follows a failure. For that, see for example Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures.

Decisions for the Organization:

  • Who reviews SI-generated artifacts, and how is their time provided as the volume of generated artifacts grows?
  • Where service must be restored before a new artifact is fully verified, is a previously verified known-good version restored instead, and who decides? (see the Safe and Valid versus Resilient tension)

References:

  • Guidance NIST SP 800-218A, Secure Software Development Practices for Generative AI and Dual-Use Foundation Models: An SSDF Community Profile, July 2024, from NIST. Section 1, Scope, states that the Profile’s practices do not distinguish between human-written and SI-generated source code, on the assumption that all source code should be evaluated for vulnerabilities and other issues before use. This is the starting position this Practice takes for machine-authored code, which it extends to configurations and procedures and to validation against tacit institutional knowledge.
  • Guidance NIST SP 800-218, Secure Software Development Framework (SSDF) Version 1.1: Recommendations for Mitigating the Risk of Software Vulnerabilities, February 2022, from NIST. Practices PW.7 and PW.8 call for human-readable code to be reviewed or analyzed and executable code to be tested, and PW.7.2 gives as an example using expert reviewers to check code for backdoors and other malicious content. Task RV.3.3 asks that software be reviewed for similar vulnerabilities to eradicate a class of vulnerabilities. Written for software generally, it bears on the deliberate weaknesses and shared flaws this Practice looks for in SI-generated code.
