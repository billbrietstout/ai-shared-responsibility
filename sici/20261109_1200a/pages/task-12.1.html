Task 12.1: Establish Governance and Accountability for SI-Generated Execution Artifacts

Giving each SI-generated artifact an owner and an approver extends the change ownership most organizations already have, and helps make clear who checked an artifact and who answers for it in service. Define the policy framework and responsibility structures for the creation, classification, and authorization of SI-generated logic. This Task helps ensure that every machine-authored artifact, from code to procedural summaries, is assigned a consequence based risk tier (see Implementation 3.1.3: Define Acceptable Risk Thresholds and Associated Control Responses) and a clear human owner responsible for its final approval and operational deployment. The general requirement to identify an accountable owner, and to establish that the organization can act on that accountability, is in Task 3.9: Assess and Document Organizational Readiness for Each SI-Enabled Capability. Where code, configurations or procedures are delivered by a vendor or integrator, procurement and acceptance terms can ask the supplier to disclose which of them were substantially SI-generated, so that the same classification and approval can be applied to them.

Main Trustworthiness Contributions:

  • Accountable: Contributes a named human owner for each machine-authored artifact and the roles authorized to promote it from draft to production, so that a generated artifact does not enter service on the SI system’s authority alone. This Task does not cover establishing the decision authority those roles sit within, which Implementation 3.9.2: Define Decision Authority and Reassessment Triggers sets out.
  • Transparent: Contributes provenance metadata linking each generated artifact to the model version, prompt and inference context that produced it, and directs validation leads to rely on that record rather than on post-hoc explanation tools. This Task does not cover defining the logging and retention arrangements that hold the record, which Task 10.1: Define Decision-Level Logging and Metadata Retention Policies covers.

Trustworthiness Side Effects to Consider:

  • Safe: A tier assigned for an artifact’s present use stays with it, and this Task’s own example suggests a draft email summary of a procedure might be classed as low risk. If that draft is later reused as the procedure itself, the tier understates the consequence. Task 3.2: Implement Independent Guardrails for SI Outputs calls for full rigor once assistant output informs an operational decision or generates a deployed configuration, and Implementation 12.1.1: Artifact Risk Classification classifies artifacts by their reach and likely reuse rather than their present use alone.
  • Secure: The provenance record and risk tier for each artifact together show which generated logic commands which assets, which SI system, prompts and sources produced it, and which artifacts are treated as highest consequence. An attacker could use this to pick targets, or to learn which prompts and sources to manipulate so that a weakened artifact is produced. Protecting these records is a matter for the organization’s existing information classification and handling practice, and Practice 10: Implement Multi-Tiered SI System Logging and Audit Capabilities sets access controls and tamper evidence for captured records of this kind.

Related AI RMF Subcategories Include:

  • MAP 5.1 (on identifying risk likelihood and impacts): This Task covers consequence-based tiering of each machine-authored artifact, distinguishing logic that commands assets directly from logic that informs human choices; it does not cover assessing how an artifact error could cascade into physical infrastructure. For that, see for example Implementation 3.1.4: SI-Generated Artifact Driven Impact Analysis.
  • GOVERN 2.1 (on establishing roles and responsibilities): This Task covers a named owner for each machine-authored artifact and the roles authorized to promote it to production; it does not cover defining the wider decision authority for the SI-enabled capability. For that, see for example Implementation 3.9.2: Define Decision Authority and Reassessment Triggers.
  • MEASURE 2.8 (on measuring accountability and transparency): This Task covers a provenance record tying each artifact to the model version, prompt and inference context behind it; it does not cover examining and documenting the transparency and accountability risks themselves.

Decisions for the Organization:

  • Who is the accountable owner for each class of SI-generated artifact?
  • What happens to ownership of an artifact in service when its owner leaves or changes role?
  • Are vendors and integrators asked to disclose which deliverables were substantially SI-generated, and in which procurement or acceptance terms?
  • What time, expertise and authority does an accountable owner need to reject an artifact, and where does that capacity come from?

References:

  • Guidance SR Letter 11-7 Attachment, Supervisory Guidance on Model Risk Management, April 2011, from the Board of Governors of the Federal Reserve System and the Office of the Comptroller of the Currency. Section VI, under Roles and Responsibilities, gives the model owner ultimate accountability for model use and has the owner confirm that models in use have undergone validation and approval. Section III describes “effective challenge” as critical analysis by objective, informed parties, and says that it depends on incentives, competence and influence. Written for bank models, it is a sector example of the owner and approval roles that this Task assigns for generated artifacts.
