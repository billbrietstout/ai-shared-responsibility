Implementation 7.3.3: Freeze Adaptation of Online-Learning SI Systems During Operational Windows

For AI systems utilizing online learning (including reinforcement learning), continuous local fine-tuning, dynamic prompt optimization, real-time retraining, or other forms of adaptation at runtime, where the organization controls the adaptation, programmatically freeze all changes to the system during operational windows.

This may include model weights (the model’s internal, learned parameters) and other online adaptation configuration parameters, such as hyper-parameters (pre-defined configuration settings that control how the model learns or operates). Boundary logic (the programmatic code defining the safe operating limits the system should stay within, as established in Task 3.2: Implement Independent Guardrails for SI Outputs) is not an adaptation parameter: the system’s own adaptation should never be able to alter it. Other changes to it, whether during an operational window or not, should be frozen for the window where appropriate and otherwise made only under the change control and version tracking of Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms, so that operators know when the limits have changed.

Shifting a deployed model from a static runtime state into a tuning cycle should require a physical confirmation step or an out-of-band administrative governance mechanism. This helps prevent streaming production data or unvetted operational telemetry from silently altering the model’s learned behavioral thresholds outside of formal configuration change control channels. Where some adaptation is permitted during operation, define what may change automatically, for example retraining on more recent data while the architecture and hyperparameters stay fixed, and record the justification for allowing it.

The freeze itself can be a software setting, such as a mode that operators can see on their displays. Turning learning back on is what needs the separate step. Otherwise anything able to change that setting, including the SI system itself, another automated process, or someone using a stolen account, could restart learning without anyone noticing. This is similar to the physical key switch found on many industrial controllers, which must be turned by hand before the controller’s program can be changed. Where a separate step is not practical, requiring two people to approve the change, alerting operators when it happens, and logging it reduces this risk but does not remove it.

Where the organization does not control the adaptation, as with an SI service whose provider updates or retrains it upstream, a freeze may not be possible at all. The options then include pinning a fixed model version where the provider offers one, requiring notice of changes under Implementation 6.1.1: Add SI Disclosure to Existing Procurement Policies, watching for changes in behavior under Task 3.4: Monitor for Anomalous SI Behavior, and relying on constraints that hold whatever the model does, under Implementation 3.2.2: Define and Independently Enforce Deterministic Operational Constraints. The remaining risk of an unannounced change should be recorded.

Examples of operational windows that may warrant a freeze include startup and shutdown, planned switching or maintenance, abnormal or emergency operation, and active incident investigation. During abnormal conditions, an adapting SI system can learn from unrepresentative data, or absorb a developing fault into what it treats as normal. Make the current state, frozen or adapting, visible to operators, and log each transition with the person who authorized it. A schedule or log of when adaptation is enabled tells an attacker when crafted data would be learned. Protecting it is a matter for the organization’s existing information classification and handling practice, balanced against operators’ need to see the current state. Where freezing would remove the function itself, such as adaptive control that tracks changing plant dynamics, or where a product offers no means to freeze adaptation, bound the adapted parameters with deterministic limits (Task 3.2: Implement Independent Guardrails for SI Outputs) and monitor them directly. Record any such gap in the asset list under Implementation 7.1.1: Create and Maintain a Master SI Asset List.

Decisions for the Organization:

  • Which operational windows call for a freeze, and what, if anything, may change automatically outside them? (see the Robust versus Valid, Reliable and Secure tension in Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms)
  • What separate step turns learning back on, and where none is practical, which compensating controls apply?

References:

  • Guidance NIST AI 100-2e2025, Adversarial Machine Learning: A Taxonomy and Terminology of Attacks and Mitigations, March 2025, from NIST. Section 2.3.5, Poisoning Attacks in the Real World, describes documented poisoning of a chatbot, an email spam filter and a malware classification service, and observes that in each case attackers crafted poisoned samples after release, relying on the model being continuously updated. This is the adversarial case for the policy lock this Implementation places on online and adaptive learning.
  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control enhancement CM-3(8), Prevent or Restrict Configuration Changes, prevents or restricts configuration changes under organization-defined circumstances, enforceable through automated mechanisms, which supports a policy lock that freezes model weights and other adaptation parameters during operational windows; treating learned parameters as configuration is this Implementation’s own extension.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Appendix F.7.5, the OT discussion of CM-3(8), Prevent or Restrict Configuration Changes, gives the example of PLC key switches that require physical access to enter programming mode, a precedent for the out-of-band step this Implementation suggests.
  • Commentary Artificial Intelligence Model Risk Management: Observations from a Thematic Review, Information Paper, December 2024, from the Monetary Authority of Singapore, written for banks. Section 6.5, under Change Management, observes that some banks update models automatically to cope with drift, and that such “dynamic AI” is subject to enhanced controls. These include justifying automatic updating and defining what may be updated automatically, for example retraining on more recent data but not changing model architectures or hyperparameters. This bears on the scope of any adaptation that this Implementation’s policy lock leaves open.
