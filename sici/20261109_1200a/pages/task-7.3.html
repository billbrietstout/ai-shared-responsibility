Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms

Keeping the mechanisms that constrain an SI system under version control helps the organization know which safeguards are in force and notice when they change. Establish rigorous configuration management and logging for the internal “wrappers,” system prompts, and safety filters built around both internal and external AI systems. Treat system prompts that contain sensitive procedures, refusal conditions or credentials as sensitive information, and keep credentials out of prompts where possible. This Task helps ensure that the mechanisms used to constrain AI behavior, including those that relate to other practices, are documented, traceable, reversible, auditable, and protected from unauthorized internal modification. As with interlocks and alarms, guardrails that block legitimate actions are natural candidates for relaxation, and a series of changes that are each reasonable can leave a mechanism weaker than the form that was validated. Review a proposed change against the hazards the mechanism was designed to address, not only against its previous version. Compare the running configuration of each mechanism with its approved version at defined intervals, so that a change made outside change control can be detected. Organizations that already manage the configuration of control system settings and software can extend that practice to prompts, filters, and other safety logic; those without established configuration management can start with the mechanisms around their highest-consequence SI systems.

Main Trustworthiness Contributions:

  • Accountable: Contributes a centralized change log for safety parameters, prompt templates and filter logic that names who authorized each change and the technical justification, with cryptographic signatures on changes to safety logic. This Task does not cover defining who is permitted to make those changes, which Task 7.4: Define Authorization and Access Controls for SI Modifications covers.
  • Secure: Contributes protection of the mechanisms that constrain AI behavior: system prompts containing sensitive procedures or refusal conditions treated as sensitive, and credentials kept out of prompts where possible. This Task does not cover determining what those mechanisms enforce, which Task 3.2: Implement Independent Guardrails for SI Outputs covers.
  • Valid: Contributes a policy lock that stops streaming data from altering learned thresholds outside change control, so that an SI system that adapts at runtime keeps operating within the thresholds that were tested, whether the data it would have learned from was unrepresentative or deliberately shaped. This Task does not cover deciding when a tuning cycle should be opened, which Implementation 2.3.4: Recurrent Risk Evaluations and Implementation 3.3.2: Establish Maximum Drift Thresholds inform.

Trustworthiness Side Effects to Consider:

  • Secure: System prompts, filter rules, and the change log describe what the safety mechanisms block, how, and how that has changed over time. An attacker could use them to craft inputs or actions that pass the filters, or to find a recently relaxed rule. Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms already treats sensitive system prompts as sensitive. Protecting the filter logic and change log is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Robust versus Valid, Reliable and Secure: Where a system adapts at runtime because its conditions shift faster than a release cycle, freezing it during operational windows holds it to conditions that may already have moved. Where the streaming data it learns from is unrepresentative, such as during an upset or a sensor fault, or can be shaped by an adversary, the same adaptation moves learned thresholds away from what was tested, without review. One way to balance this is the policy lock in Implementation 7.3.3: Freeze Adaptation of Online-Learning SI Systems During Operational Windows, which confines adaptation to deliberate tuning cycles entered through a physical or out-of-band step; others include using the drift triggers in Implementation 2.3.4: Recurrent Risk Evaluations to decide when such a cycle is opened.

Related AI RMF Subcategories Include:

  • MAP 4.2 (on establishing risk controls for AI system components): This Task makes the internal controls around an AI system, its wrappers, system prompts and filter logic, identifiable by version and traceable through each change; it does not cover deciding what those controls enforce. For that, see for example Task 3.2: Implement Independent Guardrails for SI Outputs.
  • MANAGE 4.1 (on post-deployment risk management): This Task covers change management for the safety mechanisms of deployed AI systems, through signed changes, approval and regression testing before release; it does not cover the monitoring that such plans also call for. For that, see for example Task 3.4: Monitor for Anomalous SI Behavior.

Decisions for the Organization:

  • At what intervals is the running configuration of each safety mechanism compared with its approved version?
  • Who acts when the running configuration of a safety mechanism differs from its approved version, and with what authority to restore it?

References:

  • Guidance NIST SP 800-128, Guide for Security-Focused Configuration Management of Information Systems, August 2011, with updates as of October 2019, from NIST. Section 2.3.10, Configuration Monitoring, describes activities to determine whether systems are configured in accordance with the organization’s agreed-upon baseline configurations. This is the comparison this Task asks for between the running configuration of each safety mechanism and its approved version.
