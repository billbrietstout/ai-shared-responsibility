Task 3.1: Identify Risk Trade-offs

Knowing which SI actions could do the most harm, and where, helps an organization direct its controls and attention to where the consequences are greatest. Document possible high-risk actions that the AI system may perform, including the generation of content or code, and their potential operational impacts. Maintain this documentation over time as the AI system, task, process conditions, and environment change. Record the model version, prompts, configuration, and other state and information that influenced the output that each analysis applied to, since the analysis can lose its meaning after an update or at retirement (Implementation 10.1.5: Define What Each Operational Record Is For; see also Practice 13: Establish Procedures for Retiring SI Systems and Withdrawing Their Authority). Record the tradeoff accepted at each decision point as a decision, including who made it, the evidence it rested on, and the conditions under which it should be revisited, rather than leaving it to a vendor default or to an objective set during development.

Main Trustworthiness Contributions:

  • Accurate: Contributes the error typology that gives an accuracy figure operational meaning: which kinds of error can occur at which decision point, from false positives and negatives through instruction misinterpretation to increased output latency. This Task does not cover measuring how often each occurs, which Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle covers.
  • Safe: Contributes the consequence side of the same map: how an error at each decision point reaches people, equipment or the environment, including the path where an engineer reviews AI-generated output before it becomes a deployed configuration. This Task does not cover defining the boundary that keeps the AI system away from those consequences, which Task 3.2: Implement Independent Guardrails for SI Outputs covers.

Trustworthiness Side Effects to Consider:

  • Fair: A tradeoff set to minimize total expected cost can place most of the consequence of one type of error on particular customers, locations or communities. This Task records the cost and likelihood of each error and does not ask who bears it.
  • Secure: The decision-point map in Implementation 3.1.1: Identify SI System Decision Points and Potential Outcomes of SI System Errors records where SI output reaches an operational decision, what safeguard catches an error there, and whether that safeguard depends on the SI system. It also names the decision points an adversary could manipulate, and the thresholds in Implementation 3.1.3: Define Acceptable Risk Thresholds and Associated Control Responses show how far behavior can go before the organization responds. An attacker could use these records to pick a decision point with a weak or SI-dependent safeguard. Protecting them is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Accurate versus Safe: Where one technical metric tracks the consequence closely, scoring on the metric and scoring on consequence rank the same risks first. Where the same error rate carries very different consequences at different decision points, a threshold set on the metric directs effort to the wrong place, which is why Implementation 3.1.3: Define Acceptable Risk Thresholds and Associated Control Responses points thresholds toward consequence-driven schemes rather than vulnerability scores or model confidence. One way to balance this is to keep the metric as the trigger and the consequence class as the response; others include setting a separate threshold at each decision point, or treating the metric as evidence for likelihood alone.
  • Safe versus Safe: Where the condition being detected is common and alerts are few, lowering a detection threshold to miss fewer events costs little operator attention. Where the condition is rare, the same change can multiply false alarms, and an operator handling many false alarms is less likely to act promptly on a true one. One way to balance this is to count the operator’s handling of false alarms as a cost of the threshold, using the attention limits in Task 4.4: Attention Governance and Alert/Alarm Flood Mitigation; others include routing low-confidence detections to a channel that does not interrupt the operator, or accepting more missed detections where an independent safeguard covers them.

Related AI RMF Subcategories Include:

  • MAP 5.1 (on identifying risk likelihood and impacts): This Task identifies each decision point at which an AI error changes an operational outcome, and estimates the cost and likelihood of that error across normal, degraded and emergency conditions; it does not cover extending the analysis to systems affected only through shared adjacency or shared infrastructure. For those, see for example Task 3.5: Define and Control Risks to Adjacent and Related Systems.
  • MAP 1.5 (on documenting risk tolerances): This Task sets consequence-driven threshold criteria that bound acceptable AI behavior, and ties each threshold to a defined organizational response; it does not cover identifying who may accept a risk against those thresholds. For that, see for example Implementation 3.9.2: Define Decision Authority and Reassessment Triggers.
  • MAP 2.2 (on defining AI system utility and oversight needs): This Task documents how AI output reaches an operational decision, including the second-order path where an engineer reviews AI-generated configuration or code before it is deployed; it does not specify how an operator is told that the system has reached a limit. For that, see for example Task 3.3: Establish Failure Notification Requirements.

Decisions for the Organization:

  • Which tradeoff between error types is accepted at each decision point, who accepts it, and when is it revisited? (see the Accurate versus Safe and Safe versus Safe tensions)
  • Who maintains the decision-point map and the tradeoff records as the SI system and the process change, and what prompts an update?

References:

  • Working Document Preliminary Report, October 2026, from the National Security Commission on Robotics for Advanced Manufacturing, a commission initiated by the Special Competitive Studies Project. Under Finding 7, it notes that exploits that seize control of physical manipulators would let attackers cause physical damage and prolonged disruption. Under Finding 3, it notes that a network-isolated packaging cell does not share the risk profile of a connected mobile robot in a defense production facility. These are manufacturing examples of high-risk actions, and of their dependence on deployment context.
