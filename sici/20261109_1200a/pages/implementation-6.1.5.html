Implementation 6.1.5: Operational SI Hazard Reachability Disclosures

Hazard reachability attestations help an organization judge whether a known model limitation can affect its own process as deployed, or whether other controls have made that limitation unreachable. AI vendors and system integrators should supply machine-readable hazard reachability attestations, adapting Vulnerability Exploitability eXchange (VEX) workflows, alongside AIBOM disclosures. Organizations should recognize a fundamental distinction between software-level vulnerabilities and model-level behavioral risks:

  • Deterministic Software Dependencies (Standard VEX): For traditional software libraries, machine learning frameworks (e.g., PyTorch, CUDA, vLLM), and execution drivers listed in the AIBOM, vendors should supply standard Vulnerability Exploitability eXchange (VEX) statements (e.g., CSAF or CycloneDX) that cross-reference known CVE databases to declare whether software flaws are reachable in the compiled product.
  • Probabilistic Model Behaviors (Contextual Hazard Reachability): Because no centralized, indexed vulnerability database (equivalent to CVE/NVD) exists for the stochastic failure modes of AI models (e.g., hallucination propensities, context window corruption, or distribution drift sensitivity), traditional VEX database lookups cannot be directly applied to AI model weights.

In the latter case, vendors should adapt VEX workflow principles by providing a Contextual Hazard Reachability Attestation. This attestation documents whether a known model limitation identified during TEVV (Practice 1 and Practice 2) or mapped during risk-surface scoping (Task 3.8: Scope and Map the Expanded SI Attack Surface and Risk Surface) is rendered operationally unreachable within the specific deployment architecture. This does not preclude vendors also disclosing which physical or operational hazards an SI function’s outputs can reach and through what path, which can inform the operator’s scoping under Task 3.8: Scope and Map the Expanded SI Attack Surface and Risk Surface. Reachability should be judged by what the SI system’s software, interfaces and credentials permit it to do, not only by the role it was designed for. An SI system intended to be advisory can still reach control actions if it is integrated through an interface that can write to the control system, or if prompt injection steers it to use a tool it has access to. Where a supplier declines to provide an attestation, the reachability assumed can be as broad as those interfaces and credentials permit.

Vendors declaring a model hazard as “Not Affected” should supply the machine-readable justification, such as independent safety wrappers (Task 3.2: Implement Independent Guardrails for SI Outputs), execution sandboxing (Implementation 3.5.3: Impact Compartmentalization (Sandboxing)), or strict least-agency tool restrictions (Task 5.3: Implement Principles of Least Agency and Least Privilege for SI Entities).

The existing VEX justification “Inline mitigations already exist” (see CISA 2023) is limited to protections built into the product that the user cannot configure or disable, so controls that the operator deploys around the AI system would need to be stated as a separate justification. These measures are intended to break the reachability path between the AI flaw and physical or mission consequences. As SP 800-37r2 Section 2.8 holds for external products and services, the operator generally remains responsible and accountable for the risk, including the hazard analysis of its own process. Attestations can feed the organization’s existing hazard analysis methods, for example by treating the SI component, in a process hazard analysis, as a possible initiating cause or as a layer of protection that may be degraded. Contextual Hazard Reachability Attestations used to trigger auto-suppression under Task 4.4: Attention Governance and Alert/Alarm Flood Mitigation should require either independent verification by the operator (e.g., reproducible test cases run against the actual deployment architecture) or corroboration against the operator’s own TEVV evidence (Task 1.3, Implementation 2.3.1) before being trusted to silence an alert.

Vendor self-attestation alone should not be treated as sufficient to suppress a warning. In traditional software, where the shared vulnerability database described above does exist, the tools that generate VEX data still show substantial disagreement about which vulnerabilities are present (see Churakova et al. 2026). Absent that database, a contextual attestation is harder to corroborate. An attestation should record the deployment architecture against which reachability was determined, including the tools and connections available to the SI system, its delegation depth, and the controls relied on in the justification. Where a change of the kind described in Implementation 3.8.3: Dynamic Risk Surface Coupling Analysis occurs, attestations that depend on it should be treated as unconfirmed until re-established, and any suppression under Task 4.4: Attention Governance and Alert/Alarm Flood Mitigation that rested on them should lapse rather than persist.

Decisions for the Organization:

  • Which vendor attestations, once corroborated, may downgrade or consolidate warnings, and what corroboration is required?
  • What reachability is assumed where a supplier declines to provide an attestation?

References: The application of VEX workflows and concepts to AI risk reachability is still a topic of active work. The first two references describe the state of VEX practice in traditional software, which is the basis for the caution above. The remainder are cybersecurity-specific VEX resources that may be useful as a guide for how to incorporate these principles more broadly.

  • Research Churakova, Y., Ekstedt, M., and Schmid, L., Vexed by VEX Tools: Consistency Evaluation of Container Vulnerability Scanners, in Foundations and Practice of Security: 18th International Symposium, FPS 2025, Revised Selected Papers, Part I, Lecture Notes in Computer Science volume 16402, Springer, 2026, pages 139 to 156. Open access preprint at arXiv:2503.14388. Research from KTH Royal Institute of Technology. Compares seven VEX-generation tools across 48 container images and finds a highest pairwise similarity of 69%, with most five-tool combinations agreeing on nothing at all and the best reaching 3.4%. It measures consistency between the tools that generate VEX data rather than the accuracy of any supplier’s claim, so it bears on how much weight a single unchecked attestation can carry.
  • Commentary Signal in the Noise: An Industry-Wide Perspective on the State of VEX, from the Open Source Security Foundation, a cross-industry body hosted by the Linux Foundation, drawing on contributions from Amazon, Aquasec, Chainguard, Cisco, Debian, Ericsson, Freexian, Google, Microsoft, Red Hat and OpenSUSE. Reports that “the reality today is that VEX feels more like a promise than a practice”, and that for many enterprise consumers trust is “currently based on where the file is hosted rather than cryptographic proof”.
  • Guidance CISA (2023) Minimum Requirements for Vulnerability Exploitability eXchange (VEX), from the United States Cybersecurity and Infrastructure Security Agency, the federal agency responsible for civilian cybersecurity. Specifies the minimum elements a VEX document must carry, independent of format, including the justifications a supplier gives for a “Not Affected” status. That is the model Contextual Hazard Reachability Attestations adapt.
  • Guidance CISA (2022) Vulnerability Exploitability eXchange (VEX) - Use Cases, from the same agency. Sets out scenarios with proposed implementations, showing how the minimum data elements are assembled in practice.
  • Commentary Friedman, A. (2026) Practical Guidance for Managing VEX Workflows, published by FOSSA, a commercial supplier of software composition analysis tooling that sells VEX workflow automation. Friedman led the SBOM and VEX communities at NTIA and then CISA and now advises independently, so this is one of VEX’s principal advocates describing what running it actually requires, and observing that adoption is still catching up to SBOM.
