Implementation 5.1.1: Audit for and Replace Shared Credentials, Service Accounts, Secrets, Passwords, and API Keys

Begin by finding the credentials that SI systems currently use: secrets embedded in code repositories, container images, configuration files, agent and tool definitions, notebooks and prompts, and the service accounts and API keys held in identity providers. For each, record what uses it, what it can reach and who owns it. Technically enforce distinct, cryptographically verifiable non-human identities (NHIs - credentials designed to be issued to software/AI agents rather than people) for each autonomous sub-agent, micro-service hook, or transient tool invocation at the granularity chosen under Task 5.1: Establish Identities and Authentication for SI Entities, particularly in AI systems built from multiple independent parts that each act and access resources on their own, including agentic AI systems. Where technically feasible, avoid the reuse of a single, shared enterprise API key or master service account across multiple independent agent nodes. Treat a credential used by both a person and an SI entity as shared, and give priority to shared credentials that reach OT or safety-relevant functions. For compute-constrained or legacy assets where unique cryptographic identities cannot be natively generated, enforce compensating controls at an alternative point in the system. In OT, replacing a credential that field equipment depends on can be staged within planned maintenance windows, with dependent connections confirmed and a tested way back, so that disabling the old credential does not halt a process. Where a shared credential has to remain, record its compensating controls, the owner of the risk and a date for review. Relying on shared accounts or group credentials heavily degrades situational awareness and complicates post-incident forensics because it obscures the true root cause of an action. In a complex or chained multi-agent system, being able to trace actions back to a unique, non-shared programmatic identity is essential for granular attribution and containment. Appropriately implementing granular NHIs helps ensure that if an individual model node experiences behavioral drift, runtime errors, or prompt compromise, its specific access tokens, API keys, session credentials, or similar can be isolated and revoked without invalidating the wider multi-tiered asset application architecture. Drift and runtime errors may first be noticed by operations or engineering rather than by a Security Operations Center (SOC). Who can trigger revocation in each case is the organization’s decision, within any regulatory or contractual obligations. Record it, so that whoever notices the problem knows who can act. Whoever holds that decision needs the access and authority to revoke without delay, including outside normal working hours.

Decisions for the Organization:

  • Who can trigger revocation of an SI entity’s credentials when the problem is drift or error rather than compromise?
  • Which shared credentials remain for now, with what compensating controls, risk owner and review date?

References:

  • Guidance NIST SP 800-53 Rev. 5, Release 5.2.0, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control IA-13, Identity Providers and Authorization Servers, added to the catalog after the 2020 Rev. 5 publication and included in Release 5.2.0, calls for identity providers and authorization servers to manage user, device and non-person entity (NPE) identities, attributes and access rights supporting authentication and authorization decisions, and its discussion describes the identity assertions and access tokens they issue. It is the control under which distinct non-human identities for AI agents and tools would be managed and issued.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Section 6.2.1.4.5, Password Authentication, states that shared credentials limit the ability to positively identify the person, process or device that accessed a protected resource. The OT discussion of IA-2 in Appendix F.7.7 gives increased physical, personnel and audit controls as compensating measures where shared accounts are required.
  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control enhancement IA-5(7), No Embedded Unencrypted Static Authenticators, asks that unencrypted static authenticators not be embedded in applications or other forms of static storage, and its discussion extends static storage to access scripts and function keys. This bears on the search for embedded secrets that begins this Implementation.
