Task 5.2: Determine and Implement Specific Access Requirements

Enforced access limits help keep the consequences of a compromised or malfunctioning SI entity within known bounds. Define specific systems, data sources, and tools each AI entity is authorized to access, and ensure those permissions are technically enforced and auditable against the scope of deployment and operational context. Enforce these permissions outside the SI system, at a point that it cannot bypass or alter, such as the tool, a gateway in front of it, or the downstream system. For SI systems that take natural-language instructions, an instruction such as a system prompt telling the SI system not to change setpoints guides its behavior but is not an access control. Distinguish permission to read an asset from permission to propose a change to it and from permission to execute that change, for example drafting a work order versus releasing it.

Main Trustworthiness Contributions:

  • Secure: Contributes the enforced boundary between an authenticated AI entity and the assets it may reach, recorded in a map kept current as roles and deployments change, so the reach of an entity that is compromised or malfunctions is a known quantity. This Task does not cover detecting an entity misusing access it legitimately holds, which Task 5.4: Implement Continuous Monitoring of SI Entities Against Access and Action Boundaries and Expectations covers.
  • Safe: Contributes authorization of the individual action at the moment of execution, against the requesting entity’s task scope, parameter limits and operational state, so an authenticated session carries no blanket permission for the consequential commands that follow. This Task does not cover defining the state the process enters when an action is refused, which Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior specifies.

Trustworthiness Side Effects to Consider:

  • Secure: The access map in Implementation 5.2.1: Map and Document SI Agent Access to Operational and Data Assets records which systems, data sources, and physical assets each SI agent can reach, the identities its tools connect under, and which access can change a physical process or cannot be reversed. An attacker could use it to choose the agent or tool whose compromise reaches furthest, or to find access granted outside the design. Protecting the map is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Safe versus Safe: Where the refused action is one the process can proceed without, blocking it is the safe outcome and the trade does not arise. Where the entity is part-way through a sequence, refusal can leave the process in a state that is itself hazardous, and Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior notes that a fail-safe state is not necessarily simply stopping. One way to balance this is to design what refusal means for each consequential action, so a blocked command lands in a defined state rather than in whatever state the process was in. Others include placing the authorization check before a sequence begins rather than at each step within it, or scoping the grant to the whole sequence where the steps cannot be safely separated.

Related AI RMF Subcategories Include:

  • MAP 4.2 (on establishing risk controls for AI system components): This Task records which systems, data sources and tools each AI entity may reach, and requires that record to be technically enforced and auditable; it does not cover paring those permissions back to the minimum. For that, see for example Task 5.3: Implement Principles of Least Agency and Least Privilege for SI Entities.
  • GOVERN 3.2 (on defining human-AI configuration): This Task puts the human approval point inside the runtime authorization decision, so that a consequential action is checked individually rather than granted by an authenticated session; it does not cover authorizing the people who modify AI systems. For that, see for example Task 7.4: Define Authorization and Access Controls for SI Modifications.

Decisions for the Organization:

  • Where is each permission enforced: at the tool, at a gateway in front of it, or at the downstream system?
  • What does refusal mean for each consequential action? (see the Safe versus Safe tension in Task 5.2: Determine and Implement Specific Access Requirements)

References:

  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, August 4, 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM08:2026, Hidden Context Exposure, asks that privilege separation, authorization bounds checks and similar controls not be delegated to the LLM, whether through the system prompt or another mechanism, and that they be enforced in a deterministic and auditable manner. This bears on enforcing access outside the SI system rather than by instruction.
  • Guidance Agentic Identity and Access Management, Workstream 4: Secure Design Patterns for Agentic Systems, version 1.0, 20 March 2026, from the Coalition for Secure AI, an OASIS Open Project. Section 3.4, Authorization and delegation, evaluates what an agent can do against the principal, the action (read, write, approve, execute), the resource and the conditions. This bears on distinguishing reading an asset from proposing and executing a change to it.
