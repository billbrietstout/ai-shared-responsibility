Implementation 2.2.1: Maintain Backup Systems Proportionate to Consequence

A backup that is current and ready lets an essential function continue when the SI system cannot be relied on. Establish a risk-proportionate redundancy gradient for AI-driven functions, matching the level of architectural isolation to the severity of consequences of failure, as assessed against the thresholds in Implementation 3.1.3: Define Acceptable Risk Thresholds and Associated Control Responses. For lower and moderate-consequence applications where non-AI fallbacks are technically infeasible, organizations should deploy heterogeneous AI redundancy, utilizing secondary models built on distinct architectures, training distributions, and hosting infrastructure to mitigate single-points-of-failure and shared model drift. Where a non-AI fallback, such as a documented manual procedure, is feasible, it remains an option at any consequence level. For high-consequence or cyber-physical functions, redundancy should escalate to include independent, deterministic algorithmic fallbacks or out-of-band non-AI physical safety interlocks (Implementation 3.2.2: Define and Independently Enforce Deterministic Operational Constraints). Develop and communicate expected guarantees of performance during fail-over procedures so that downstream entities can prepare for potential impacts. Keep the backup current with the primary. Configuration changes, such as new equipment, revised limits or renamed tags, should be carried into the backup through the same change process. Keeping a backup current takes ongoing effort, and resourcing it is part of the redundancy decision (see Task 11.3: Pre-Allocate Operational Resources for Alternative Service Delivery). Where an existing conventional control scheme is retained as the backup, it should keep its tuning, alarms and interlocks once the AI system is introduced. For periodic confirmation that backup infrastructure still functions, see Implementation 11.3.2: Maintain Isolated Standby Infrastructure and Allocated Reserves.

Decisions for the Organization:

  • For which functions is a fallback independent of the SI system infeasible, and is heterogeneous redundancy accepted there? (see the Resilient versus Resilient tension in Task 2.2: Establish Requirements for Redundancy in SI-Driven Functions)

References:

  • Guidance NIST SP 800-160v2r1, Developing Cyber-Resilient Systems: A Systems Security Engineering Approach, from NIST. Section D.5.2.5, Plan and Manage Diversity, warns that diversity can be more apparent than real, as when alternative implementations run on the same underlying operating system or reuse software components, and calls for analysis of the architectural approach to diversity. This applies to secondary models that share a foundation model, training data or hosting provider. Table D-4 makes the same point for the Diversity technique, noting that reliance on common libraries and infrastructures means analysis is needed to verify the extent of diversity. Its Design Diversity approach (for example, N-version programming and mixed hardware and software implementations) and Supply Chain Diversity approach (using multiple independent supply chains for critical components, with the example of analyzing components from different suppliers for common elements) correspond to the levels of independence in this redundancy gradient.
