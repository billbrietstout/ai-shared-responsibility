Implementation 3.5.4: Define and Implement Resource Limiting

Limits on an SI system’s use of shared resources help keep other systems, including safeguards, supplied when an agentic system consumes resources quickly. Limits set too tightly can starve the SI system itself, so they are a balance against what its task needs. Identify limited resources that the AI agent or system shares with other systems (AI or otherwise), such as compute, tokens, exclusive hardware/sensor access, power, network bandwidth, and cooling. Define and implement appropriate soft and hard limits on the AI system’s use of these resources, along with appropriate notifications for when these limits are approached or exceeded. Where consumption accumulates quickly, it can outpace a notification, so a hard limit should stop the consumption rather than only report it. Include the resources that monitoring, logging and enforcement controls themselves depend on. Where these share a host with the SI system, a runaway agentic loop can exhaust that host before those controls act, so place them on separate resources or reserve capacity for them. Spare capacity that depends on other workloads staying idle is not a reserve. Where the SI system competes for the same power, compute, cooling or bandwidth as the physical or public service it supports, establish in advance which SI workloads yield, and in what order, so that the SI system does not take resources that the mission itself needs. Enforce these limits outside the SI system, for example at a gateway, in the operating system, in the orchestration layer or at the controller, so that the SI system cannot raise them.

For agentic and multi-agent systems, these limits can include per-agent budgets for tokens, time and tool calls that fail closed when exceeded. They can also include a circuit breaker that halts an agent after a defined number of consecutive failed or anomalous actions. Bound retries with randomized backoff and a retry budget, so that one agent caught in a retry loop cannot saturate a dependency it shares with others. Retrying at several layers at once multiplies the attempts that reach that dependency. Idempotency keys on state-changing actions can mean that a retried action is not carried out twice.

Decisions for the Organization:

  • Where are the soft and hard limits set for each shared resource?
  • Which SI workloads yield first, and in what order, when a shared resource runs short? (see the Safe versus Reliable tension in Task 3.5: Define and Control Risks to Adjacent and Related Systems)

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control SC-6, Resource Availability, protects the availability of defined resources by allocating them by priority or quota, so that lower-priority processes cannot delay higher-priority ones and no process obtains more than a predetermined amount, which is the control form of the limits this Implementation places on an AI system’s share of compute, bandwidth and other shared resources.
  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM06:2026, Unbounded Consumption, notes that agentic architectures and tool-use protocols can amplify a single request into cascading downstream operations. Its mitigations include hard spending caps that halt inference when exceeded, rather than alerting thresholds that fast-accumulating workloads can outpace, and agentic circuit breakers with step, recursion-depth, time and per-run cost limits. These bear on the hard limits and agent budgets in this Implementation.
  • Commentary Ulrich, M., Addressing Cascading Failures, Chapter 22 of Site Reliability Engineering: How Google Runs Production Systems, 2017, from Google, published by O’Reilly Media. Under Retries, it shows how naive retries can keep an overloaded backend from recovering. It recommends randomized exponential backoff, a limit on retries per request, and a server-wide retry budget beyond which requests fail rather than retry. It shows how retrying at several layers multiplies attempts. Under Resource limits, it cautions against relying on slack capacity whose availability depends on other jobs. These bear on bounded retries and on reserved capacity in this Implementation.
