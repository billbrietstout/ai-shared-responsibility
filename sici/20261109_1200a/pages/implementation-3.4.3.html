Implementation 3.4.3: Monitor Validation Control Integrity

Checking that guardrails and watchdogs are still enforcing lets an organization rely on what they do, not only on their presence in a record. Establish continuous monitoring of the states of the validation controls (the safety wrappers of Task 3.2: Implement Independent Guardrails for SI Outputs and the watchdogs of Implementation 2.2.2: Deploy “Watchdog” Controllers) to validate that mechanisms are actively and correctly functioning. This includes confirming that each control is operating in its intended enforcement state, blocking or otherwise acting on a violation rather than only detecting or alerting on it, since a control left in a detect-only or alert-only mode can appear in inventories and assurance records as implemented while stopping nothing. Confirm this state in the production configuration at commissioning and after changes made under Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms. Where practical, confirm it by exercising the control, for example by presenting a known out-of-bounds test command in a test or maintenance mode and confirming, from records independent of the control, that it was refused, rather than relying on the control’s own report of its state. Confirm that each control remains in the path it was placed in, for example by reconciling the number of SI outputs produced with the number the control evaluated, and by checking for output paths that do not pass through the intercept points identified in Implementation 3.2.1: Identify SI Output Intercept Points. Check the code, rule sets and configuration of each control against the approved versions held under Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms, at startup and at a defined frequency. Where a control is bypassed or overridden, record who authorized it, when it began and when it is due to end, and raise a notification if it remains in place past that time. Run this monitoring separately from the controls it checks, with its own credentials and hosting where practical. Define in advance whether the SI-enabled function continues, is restricted, or moves to the fallback in Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior when a control is found not to be functioning.

Decisions for the Organization:

  • What happens to the SI-enabled function when a validation control is found not to be functioning?

References:

  • Guidance NIST SP 800-137, Information Security Continuous Monitoring (ISCM) for Federal Information Systems and Organizations, from NIST. Section 3.2.1, Determine Metrics, states that metrics are fundamentally flawed without assurance that all security controls are implemented correctly, that collecting metrics from security controls that have not been assessed is like using a broken or uncalibrated scale, and that without assurance of the correct implementation and continued effectiveness of controls not associated with a metric, root-cause analysis may be narrowed to a predetermined list and overlook the true problem. This supports monitoring the state of the validation controls themselves rather than only what they report.
  • Guidance NIST SP 800-160v2r1, Developing Cyber-Resilient Systems: A Systems Security Engineering Approach, from NIST. Section D.5.2.1, Limit the Need for Trust, states that where a system element is required to have a given level of trustworthiness, some attestation mechanism is needed to verify that it has and continues to retain it, which applies to the validation controls in Task 3.2 that the rest of the system relies on. Section D.5.2.8, Leverage Health and Status Data, cautions that components can report health and status data erroneously or maliciously, so a control reporting itself as active is not by itself evidence that it is enforcing.
  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control SI-7, Software, Firmware, and Information Integrity, employs integrity verification tools to detect unauthorized changes to defined software, firmware and information, and enhancement SI-7(1) performs those integrity checks at startup, at defined transitional states or events, or at a defined frequency. These bear on checking each control against its approved version.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Their Executive Summary says that the keys of OT assets such as programmable logic controllers and safety systems should be in the “Run” position at all times unless they are being actively programmed. This is the OT counterpart of confirming that a validation control is in its intended enforcement state, not only that it is present.
