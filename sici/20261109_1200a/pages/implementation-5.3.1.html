Implementation 5.3.1: Determine the Practical Minimum Necessary Permissions for a Specific Task and Apply Them to the SI System

Starting from the access map in Implementation 5.2.1: Map and Document SI Agent Access to Operational and Data Assets, pare each AI agent’s permissions down to only what its current task requires, removing standing access to systems it does not actively need. For example, an AI system that only reads sensor telemetry should never retain write access to control setpoints, even if it was granted that access during initial testing. The same paring applies to the tools offered to the SI system and to what each tool can do. A tool that the task does not need should not be offered, and a narrowly defined tool, such as one that only writes a specific file, is preferable to an open-ended one, such as a general shell command. Enforce the reduced permissions on the identity that each tool uses to connect to downstream systems, rather than relying on the SI system to observe them. Where the organization has a suitable test environment or digital twin, one way to find the practical minimum, and to see what a tighter limit would stop the system doing, is to run the SI system in it (Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior) across representative and unusual scenarios, record the permissions it uses, and remove those it does not. Scenarios not exercised in testing can still call for a permission, and permissions pared so tightly that the SI system routinely fails can lead to broad, undocumented exceptions. Where a needed permission is missing, decide whether to grant it with a recorded reason, redesign the task, or route that step to a person or a separate tool.

Decisions for the Organization:

  • When a needed permission is missing, is it granted with a recorded reason, is the task redesigned, or is the step routed to a person or a separate tool?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control AC-6, Least Privilege, applies least privilege to system processes as well as users, so that they operate at privilege levels no higher than necessary, which extends to AI agents running as processes. Control enhancement AC-6(7), Review of User Privileges, reviews assigned privileges at a defined frequency and removes those whose need cannot be revalidated, which is the step that removes standing access an AI system no longer needs, such as write access granted during testing.
  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM03:2026, Excessive Agency, opens its mitigations with minimizing the tools an agent may call, minimizing what each tool can do, avoiding open-ended tools such as running a shell command in favor of narrowly defined ones, and minimizing tool permissions. It asks for the permissions to be enforced on the identity that each tool uses to connect to the downstream system. This bears on paring permissions back at the level of tools.
