Implementation 10.1.2: Runtime Telemetry and Artifact Tracking

Linking each output to the inputs, model version, settings, and other state and information that produced it helps an organization explain and check that output later, even after the SI system has changed. More detail costs more to store and review. Capture runtime telemetry at an appropriate level of abstraction. Where these records may serve as evidence, Implementation 10.2.2: Protect Logs from Alteration Where They Serve as Evidence covers protecting them from later change. For generated execution artifacts (such as code, Programmable Logic Controller (PLC) logic, configurations, or automated procedures), logs should uniquely link the output to the specific model version and prompt context. For AI systems providing operational decision support or diagnostics from structured data, runtime telemetry should capture an ‘inference receipt’, logging the specific data elements selected, active threshold criteria, and versioned configuration parameters that generated the output, alongside any execution artifacts. Where the AI system applies encoded rules or a self-interpretable model, the receipt can also record the rules or branches that were applied, which provides the trace displayed under Implementation 4.6.3: Display Execution Traces from Symbolic, Hybrid, and Self-Interpretable Components. Versions can be identified by the unique identifiers held in the registry of Task 7.3: Manage Version Control and Logging for Internal SI Safety Mechanisms, such as a cryptographic hash of the model, prompt template or rule set, rather than by a label that could be reused or misapplied. Where a log records sensor data or retrieved documents by reference rather than by content, the referenced source should be retained and protected for as long as the log, or a hash of the content recorded with the reference. Retaining referenced sources adds storage and management overhead. A hash costs less, but it can only show that content has changed, not recover it.

Where possible, records of what action was taken, and whether it was permitted, should be generated by the enforcement or validation layer at the point of action (see Task 3.2: Implement Independent Guardrails for SI Outputs) rather than reported by the SI system about itself. Some records, such as prompt context or the data elements a model selected, can only come from the AI system or its runtime. Where a record depends on the system it describes, its integrity is bounded by that system’s integrity, and the dependency should be documented. The same applies to changes in an SI system’s delegated authority (granted, restricted, suspended, reverted or restored), recorded with the decision that authorized them, and to refused attempts to act beyond the current authority. These records are the evidence that Implementation 3.9.5: Demonstrate Operational Enforceability relies on. Where the process can tolerate the delay, the record of the authorization decision for a consequential action can be committed to tamper-evident storage (Task 10.2: Establish Data Integrity and Tamper-Evidence Controls for Telemetry and Logging) before the action executes, so that no such action takes effect without a record.

This contributes technical evidence for validating static governance records during audits or post-incident reviews. Statistical hypotheses generated after the fact by post-hoc evaluation tools (such as LIME or SHAP) should not be relied on as a substitute for decision-level logs at the level the organization has chosen. See Implementation 8.1.2: Identify SI Systems that May Not Satisfy Root Cause Analysis Requirements for further details.

Decisions for the Organization:

  • For which consequential actions is the authorization record committed before the action executes, and how is it captured where the process cannot tolerate the delay?
  • For sources logged by reference, is the source retained and protected, or is a hash of its content recorded?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control AU-3, Content of Audit Records, has each record establish what type of event occurred, when and where it occurred, its source, its outcome and the identities associated with it. The discussion of enhancement AU-3(1), Additional Audit Information, names the access control or flow control rules invoked as information to consider adding. This bears on recording at the point of action whether an action was permitted, and under which rule.
  • Guidance AI Incident Response Framework, Workstream 2: Preparing Defenders for a Changing Cybersecurity Landscape, version 1.0, 27 October 2025, from the Coalition for Secure AI, an OASIS Open Project. Section 3.2, Monitoring and Telemetry, lists attributes to capture at the input, processing and output stages of AI workflows, including the raw prompt and completion text, the model name and version, retrieved documents, tool calls, and a trace or session identifier that correlates activity across services. It offers a published field list against which the inference receipt in this Implementation can be compared.
