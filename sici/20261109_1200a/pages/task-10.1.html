Task 10.1: Define Decision-Level Logging and Metadata Retention Policies

Deciding in advance what each SI system records, and for how long, helps an organization reconstruct what the system did and why. Specify the AI systems and applications for which information, including system inputs, outputs, system prompts, and version-specific metadata, will be captured to help ensure automated actions are deterministically reconstructable or statistically reproducible, and overall performance is continuously monitored. How long to retain decision-level records is for the organization to decide, within any regulatory or contractual obligations. Applicable sector or regulatory requirements, the time needed to detect slow drift in the accumulated record, and any legal or contractual hold pull toward longer retention. Privacy obligations to delete personal information, and the storage load described under Implementation 10.2.1: Ensure that Existing Logging Facilities Can Absorb SI Logging, pull toward shorter. Record the retention period and the reason for it. Decide in advance what an SI system does when it cannot write the records required of it, such as continuing with an alert to personnel, restricting itself to advisory output, or halting and entering its fallback state (Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior). Record rejections and overrides of SI outputs by personnel as carefully as acceptances, for use in the review under Task 10.3: Implement Systematic Audit Review and Performance Trend Analysis.

Organizations with established logging policies can build on them. Logging policies should extend beyond traditional network event logs to capture telemetry across the entire AI Risk Surface (Task 3.8: Scope and Map the Expanded SI Attack Surface and Risk Surface), helping ensure forensic investigators can evaluate safety violations, explainability gaps, and accuracy degradation across the asset lifecycle. This Task contributes to the evidentiary foundation for transparency. It helps the organization hold the runtime context needed for the forensic root-cause analysis described in Practice 8: Incorporate SI-Aware Incident Analysis and Response Procedures. The same records support the success metrics of Practice 1: Establish Requirements for Success and help verify the bounds described in Practice 2: Define SI Robustness, Resilience, and Quality of Service Expectations.

Main Trustworthiness Contributions:

  • Transparent: Contributes capture of inputs, outputs, system prompts and version metadata for AI systems that take or directly influence mission-critical actions, with records of what was done and whether it was permitted generated, where possible, by the enforcement layer rather than reported by the SI system about itself. This Task does not cover protecting those records from alteration once captured, which Task 10.2: Establish Data Integrity and Tamper-Evidence Controls for Telemetry and Logging covers.
  • Explainable & Interpretable: Contributes the inference receipt described in Implementation 10.1.2: Runtime Telemetry and Artifact Tracking, which records the data elements selected, the active thresholds, the versioned configuration and, where applicable, the rules applied, so that an account of how an output was reached can draw on a contemporaneous record rather than on a post-hoc hypothesis such as LIME or SHAP. This Task does not cover presenting that account to personnel at the time of a decision, which Task 4.6: Ensure that Confidence and Rationale Shown to Personnel Reflect How the SI System Reached Its Output covers.

Trustworthiness Side Effects to Consider:

  • Reliable: Capturing telemetry across the AI Risk Surface adds bandwidth and storage load to logging facilities that other systems already depend on, and can crowd out logging from edge devices or cause existing logs to be deleted earlier than required. Implementation 10.2.1: Ensure that Existing Logging Facilities Can Absorb SI Logging asks for that check before AI logging is added, and Implementation 10.1.4: Asynchronous Telemetry and Inference Logging for Constrained Edges covers environments where continuous transfer is not feasible.
  • Secure: Decision-level records capture system prompts, inputs, active thresholds, and version identifiers. In an attacker’s hands, they show how the SI system is instructed, what its guardrails block, and how close an input can come to a threshold without triggering a response. Task 10.2: Establish Data Integrity and Tamper-Evidence Controls for Telemetry and Logging covers protection against alteration and unauthorized access. How the records are classified and who may read them is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Privacy-Enhanced versus Transparent: Where logged inputs and outputs are machine telemetry and configuration, full capture costs little in privacy. Where the AI system processes sensitive person-centric data, such as healthcare clinical support decisions or smart meter consumption records, the raw prompts and outputs that forensic reconstruction needs are themselves the protected data, and masking them in day-to-day repositories removes what an investigator would look for. One way to balance this is the arrangement in Implementation 10.1.3: Forensic Integrity and Privacy-Preserving Log Partitioning, which defines the fields essential to root-cause reconstruction, restricts masking to the rest, and routes the unredacted record into tamper-evident storage logically separated from routine operational visibility; others include limiting what is captured to the elements identified in the privacy risk assessment.

Related AI RMF Subcategories Include:

  • MEASURE 2.9 (on measuring interpretability and explainability): This Task covers the inference receipt and decision-level record against which an output can be interpreted within its context, in place of after-the-fact attribution; it does not cover how that interpretation is presented to personnel. For that, see for example Task 4.6: Ensure that Confidence and Rationale Shown to Personnel Reflect How the SI System Reached Its Output.
  • MEASURE 2.10 (on measuring privacy): This Task covers the separation of logged fields essential to reconstruction from those that can be masked, and the routing of unredacted records away from routine view; it does not cover examining the privacy risk of the AI system beyond its logs. For the privacy impact assessment at significant updates, see Implementation 7.5.3: Integrate Privacy Impact Assessments (PIA) into Update Cycles.

Decisions for the Organization:

  • Which SI systems and applications have decision-level records captured, and what is captured for each?
  • How long are decision-level records retained, and for what reason?
  • What context, such as model version, prompts, retrieval sources, and configuration, is kept with decision-level records so that they stay interpretable after the SI system that produced them is updated or retired?
  • What does each SI system do when it cannot write its required records: continue with an alert, restrict itself to advisory output, or halt and enter its fallback state?
  • Which logged fields are essential to reconstruction and which are masked? (see the Privacy-Enhanced versus Transparent tension in Task 10.1: Define Decision-Level Logging and Metadata Retention Policies)
  • Who sets and maintains the logging policy for each SI system, and what storage, staff time, and tooling does it need?
  • Who may read decision-level records, given what they reveal about how the SI system is instructed and guarded?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control AU-2, Event Logging, identifies the event types a system can log, specifies those to be logged, coordinates the selection with other entities needing audit information, and calls for a rationale that the selected event types are adequate to support after-the-fact investigations, which is the test this Task applies when extending logging to AI inputs, outputs, prompts and version metadata. Control AU-5, Response to Audit Logging Process Failures, alerts defined personnel when audit logging fails and takes further organization-defined actions, which its discussion says can include shutting down the system. This bears on deciding in advance what an SI system does when it cannot write its required records.
  • Working Document NIST SP 800-92r1 ipd, Cybersecurity Log Management Planning Guide, initial public draft, October 2023, from NIST. Play TS-2, Define Target State for Log Generation, has the organization determine for each type of log source which events it should or must log, which data characteristics to record for each event, and whether it might capture sensitive data such as personal information, passwords or access tokens. Its supporting information notes that recording more log data is not necessarily better. This bears on deciding, system by system, what this Task captures.
  • Guidance Agentic Identity and Access Management, Workstream 4: Secure Design Patterns for Agentic Systems, from the Coalition for Secure AI. Appendix E, Governance and logging, specifies a log entry for each significant agent action that captures the agent and subject identifiers, the resource and action, the allow or deny decision with its reason, the scope and authorization details used, the policy version and attestation information, with a correlation identifier linking related events across agents in the same workflow. It is the authorization-side counterpart to the inference receipt in Implementation 10.1.2: a record of what permitted an action, and under which policy version, as well as what produced it.
