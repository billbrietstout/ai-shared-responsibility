Task 2.3: Establish Protocols for and Regularly Perform Systematic and Achievable Testing, Evaluation, Validation, and Verification (TEVV)

Perform rigorous testing and analysis specifically focused on the AI system’s behavior in anomalous or edge-case conditions and environments, extending the TEVV protocols established in Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle to govern specialized boundary and stress conditions. This Task contributes verifiable evidence that fail-safe mechanisms and manual overrides operate as intended, supporting long-term reliability. It also supports rigorously identifying the attack and risk surface as discussed in Task 3.8: Scope and Map the Expanded SI Attack Surface and Risk Surface and supports the evaluation of downstream risk as discussed in Task 3.5: Define and Control Risks to Adjacent and Related Systems.

Where an AI system can produce different outputs from the same input, as many generative AI systems and some planners that use randomized search can, a single test run may not represent its behavior. Running each test case repeatedly and reporting the spread of results, as well as the typical result, can help show how often a failure occurs. Boundary and stress tests should exercise the AI function as it is integrated with the systems around it, including the control system, the operator interface and the fallback path, as well as the AI component on its own. Incidents, near-misses reported under Task 8.6: Establish Non-Punitive Reporting for SI-Related Near-Misses and interventions by the watchdog controllers of Implementation 2.2.2: Deploy “Watchdog” Controllers can each add a case to the edge-case test set, so that later testing covers conditions the AI system has already met in service.

Main Trustworthiness Contributions:

  • Robust: Contributes evidence of how the AI system behaves beyond the conditions it is expected to meet, by exercising it against edge cases, injected faults and stressed physical, network and human parameters in environments built for destructive testing (Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior). This Task does not cover setting the criteria that the results are judged against, which Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle sets as the anchor for TEVV throughout this profile.
  • Reliable: Contributes conformance over time as a measured quantity: a curated set of normal and known-fault inputs kept current, an initial high-frequency window that measures how fast this deployment actually diverges, and an evaluation cadence derived from that measured rate (Implementation 2.3.1 and Implementation 2.3.4). This Task does not cover detecting an acute departure between evaluations, which Task 3.4: Monitor for Anomalous SI Behavior covers through continuous runtime monitoring.
  • Resilient: Contributes the evidence that the fallback path works when called on, by injecting equipment trips, sensor failure modes and mistimed interventions rather than assuming the response to them (Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior). This Task does not specify the states themselves; Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior does that.

Trustworthiness Side Effects to Consider:

  • Safe: Boundary, adversarial and destructive testing places the AI system into the conditions it exists to avoid. Implementation 1.3.2: Categorization of Testing Environments restricts that testing to staging mirrors, hardware-in-the-loop rigs, simulators and digital twins where the production path cannot absorb the disruption.
  • Secure: The failure mode map, the edge-case test set, and the test results record which failure modes the SI system is exposed to and which would pass unnoticed (Implementation 2.3.2: Targeted Failure Mode Mapping). A digital twin detailed enough for this testing also describes the process in detail (Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior). An attacker could use these to choose an input or fault that detection is known to miss. Protecting them is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Valid versus Safe: Where the deployment has planned downtime or can absorb a temporary outage, evidence gathered on the live system is the evidence that applies to it, and Implementation 1.3.2: Categorization of Testing Environments treats that as preferable. Where the process cannot tolerate disruption, the evidence has to come from a twin or a rig whose behavior may differ from the installed system in the respects being tested. One way to balance this is the pairing described in Implementation 2.3.3: Use Digital Twins to Regularly Test SI System Behavior, which combines twin-based evaluation with passive shadow mode or phased commissioning and compares live telemetry against twin predictions so that divergence stays measured. Others include limiting the claims drawn from twin results to the conditions the twin is known to reproduce.

Related AI RMF Subcategories Include:

  • MEASURE 2.3 (on ensuring realistic measurement): This Task covers the high-fidelity digital twins and hardware-in-the-loop rigs that reproduce deployment conditions closely enough for destructive and edge-case testing; it does not cover deciding when testing on the live production path is permissible. For that, see for example Implementation 1.3.2: Categorization of Testing Environments.
  • MEASURE 2.1 (on documenting measurement approaches): This Task covers the validated standard dataset of curated normal and known-fault inputs, kept current against drift, as the documented test set; it does not cover setting the pass/fail criteria that the dataset is exercised against. For those, see for example Task 1.3: Implement Evaluation and Test Plans, Including TEVV, Across the SI Lifecycle.
  • MEASURE 3.1 (on tracking known and emerging risks): This Task covers the recurrent and trigger-based re-evaluation that tracks drift and emergent behavior from actual performance in deployed contexts; it does not cover setting the drift limits at which a fail-safe response becomes necessary. For those, see for example Implementation 3.3.2: Establish Maximum Drift Thresholds.

Decisions for the Organization:

  • Which edge-case tests run on digital twins or rigs, and how is their fidelity to the deployed system checked? (see the Valid versus Safe tension in Task 2.3: Establish Protocols for and Regularly Perform Systematic and Achievable Testing, Evaluation, Validation, and Verification (TEVV))
  • What testing capacity, such as digital twins, test rigs, subject matter expert time, and test windows, is funded for edge-case testing, and what is relied on where it is not available?

References:

  • Research NIST AI 800-4, Challenges to the Monitoring of Deployed AI Systems, March 2026, from NIST. Section 3.1.1, under the barrier of uncertainty and variability in results, cites earlier NIST work noting that an AI agent instructed to perform the exact same task twice may produce different results each time. This bears on repeating test cases and reporting the spread of results rather than relying on a single run.
