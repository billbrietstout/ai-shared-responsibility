Task 7.2: Validate, Select, and Prepare Data for SI Systems

Knowing where data came from, and choosing what each SI system receives, helps the organization judge whether an SI system’s inputs are fit for its task. Document the source, cleaning process, permitted use policies, and authorization of internal datasets (e.g., maintenance logs, sensor telemetry) used to train, fine-tune or prompt AI models, and decide which of the available data each AI system should receive, and in what form. This includes operational data supplied by customers, partners or connected systems and processed by the SI system at runtime, together with the extraction, mapping and transformation steps applied to it before it reaches the SI system. This Task improves visibility into the risk of internal “data silos” that introduce biased or unvetted information into AI systems, whether for training or in retrieval-augmented or agentic systems. This visibility can also highlight opportunities to leverage data across departments while maintaining appropriate protections for that data. The outputs of this task should be documented as set out in Implementation 7.1.2: Maintain a Data Inventory. Selecting and preparing what an AI system receives, at training and at runtime, also limits what it can learn from, be influenced by, or expose (Implementation 7.2.4: Select and Prepare the Inputs Each SI System Receives).

Main Trustworthiness Contributions:

  • Bias Managed: Contributes visibility into internal data silos that introduce biased or unvetted information, extended by Implementation 7.2.3: Assess the Conditions Under Which Source Data Is Created to capture conditions that systematically drop or distort records before the data ever arrives, where certification of what did arrive cannot see the loss. This Task does not cover evaluating bias in the AI system’s outputs, which Task 10.3: Implement Systematic Audit Review and Performance Trend Analysis addresses.
  • Secure: Contributes a tamper-evident trail from source to AI system output for critical data, using cryptographic hashing and lineage tools, so that deliberate insertion or alteration of training or retrieval data can be traced. This Task does not cover restricting who may modify the data, which Task 7.4: Define Authorization and Access Controls for SI Modifications covers.
  • Valid: Contributes inputs chosen and represented for the AI system’s task, and checked at runtime against the conditions under which it was tested, so that it is not relied on for data it was never validated with. The same hashes and lineage show where data reaching the SI system differs from what was certified, whether through corruption in transfer, overwriting or a wrong version, so that it is not trained on, or relying on, data that no one has checked. This Task does not cover setting the thresholds at which a shift from those conditions calls for action, which Implementation 3.3.2: Establish Maximum Drift Thresholds covers.

Trustworthiness Side Effects to Consider:

  • Privacy-Enhanced: Where critical data includes personal information, a source-to-output trail protected from alteration keeps a record that retention limits or deletion obligations may later require to be removed. Implementation 10.2.2: Protect Logs from Alteration Where They Serve as Evidence gives ways to reconcile the two.
  • Secure: Documentation of data sources, their preparation, and the SI systems they feed shows where inserted or altered data would have the most effect. An attacker could use it to aim poisoning at a weakly protected source that reaches a consequential SI system. Protecting this documentation is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Valid versus Robust: Where anomalous records are sensor faults or entry errors, filtering them out improves the data an SI system learns from. Where they record genuine abnormal conditions, such as trips, startups, equipment failures or storms, the same filtering can remove the conditions the SI system most needs to recognize. Options include deciding with operations staff whether each class of outlier is a fault or a genuine condition. Where outliers are removed, the resulting gaps in coverage can be recorded in the data inventory under Implementation 7.1.2: Maintain a Data Inventory.

Related AI RMF Subcategories Include:

  • MAP 2.3 (on applying scientific methodologies): This Task covers documentation and certification of the suitability of internal data for an AI system, extended upstream to the field conditions in which records are created or lost, and the selection and preparation of the inputs the system receives; it does not cover experimental design or construct validation.
  • MEASURE 2.11 (on measuring fairness, accuracy, and bias): This Task identifies where internal data sources and capture conditions introduce biased or systematically incomplete data before it reaches an AI system; it does not cover evaluating the bias in that system’s outputs. For that, see for example Task 10.3: Implement Systematic Audit Review and Performance Trend Analysis.

Decisions for the Organization:

  • Who decides whether each class of outlier is a fault or a genuine condition? (see the Valid versus Robust tension in Task 7.2: Validate, Select, and Prepare Data for SI Systems)
  • Who provides the expertise and time to document and certify data sources, and what happens to data that cannot be certified in time?

References:

  • Guidance NIST AI 100-2e2025, Adversarial Machine Learning: A Taxonomy and Terminology of Attacks and Mitigations, March 2025, from NIST. Section 2.3, Poisoning Attacks and Mitigations, covers adversarial manipulation of training data, and the mitigations in section 2.3.2 include protecting training data with access controls, data sanitization and validation, and mechanisms for dataset provenance and integrity attestation. Section 3.4.2 adds knowledge base poisoning, where a document inserted into a retrieval-augmented system’s knowledge base steers its output, which is the retrieval case this Task also covers.
  • Guidance NIST SP 800-218A, Secure Software Development Practices for Generative AI and Dual-Use Foundation Models: An SSDF Community Profile, July 2024, from NIST. Task PW.3.2, under practice PW.3, Confirm the Integrity of Training, Testing, Fine-Tuning, and Aligning Data Before Use, asks that the provenance of all such data be tracked when known and that data without known provenance be documented, and its note N1 records that provenance cannot always be verified but is still worth tracking. This is the development-side form of the documentation this Task asks for when an organization fine-tunes a model on its own data.
