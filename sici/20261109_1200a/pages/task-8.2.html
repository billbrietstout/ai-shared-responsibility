Task 8.2: Identify Additional Controls that May Be Required in Scenarios Where Deterministic Root Cause Analysis Is Not Possible

Planning in advance for SI systems whose failures cannot be traced to a cause helps the organization make informed, defensible decisions about deploying and re-commissioning them. Establish formal risk-based protocols and alternative verification standards for scenarios where a precise root-cause identification is not possible, for example because the SI system is non-deterministic or opaque. Where regulation requires forensic root cause analysis, that requirement governs. Where the need rests on a safety obligation the organization has identified, whether to deploy such a system, and on what compensating controls, is for the organization to decide, within any regulatory or contractual obligations. Substituting a system that supports root cause analysis keeps the investigative path open but may give up capability; compensating controls keep the capability but need to be shown to close the gap. Record the decision and its basis. Some applications and situations may allow a root cause requirement to be relaxed; Implementation 8.2.1: Identify Applications and Situations for Which Root Cause Analysis Requirements May Be Relaxed covers identifying them, and the organization defines and documents a margin when it does so. Compensating controls that depend as little as practical on the SI system, such as the independent guardrails in Task 3.2: Implement Independent Guardrails for SI Outputs or a deterministic check of its output of the kind described in Task 2.2: Establish Requirements for Redundancy in SI-Driven Functions, can be relied on whether or not the SI system’s failure can be traced. Where the SI system’s failure cannot be traced to a cause, an investigation can still establish why these surrounding controls did or did not contain it. Where an incident involving such a system leaves its cause unknown, re-commissioning may need to rest on re-validation of its behavior, such as the shadow-mode comparison in Implementation 11.4.2: Implement “Shadow Mode” Validation and Independent Safety Protection Checks for SI Re-Commissioning, with operation on a fallback in the meantime, where the organization has prepared one (see Task 11.2: Define Manual and Alternative Operating Procedures for Long-Term Mission Continuity). Operating on a fallback brings its own considerations, such as reduced capacity and manual skills that may have faded (see Task 3.6: Mitigate Automation Complacency and Skills Degradation).

Main Trustworthiness Contributions:

  • Safe: Contributes a basis for deciding whether and how to deploy systems whose failures cannot be traced to a cause. Where regulation requires root cause analysis, that requirement governs. Otherwise, the organization records whether compensating controls close the gap, and sets margins beyond which control passes to manual oversight or to a fallback whose own failures can be traced and that shares as few of the SI system’s sources of error as practical, with those it does share identified, such as a verified-safe legacy system (Implementation 8.2.2: Identify Opaque Systems and Appropriate Safety Margins). This Task does not cover enforcing those margins at runtime, which Task 3.2: Implement Independent Guardrails for SI Outputs covers.
  • Accountable: Contributes a documented, defensible basis for each decision to deploy or re-commission such a system, including the margin the organization defines and documents when it relaxes a root cause requirement (Implementation 8.2.1: Identify Applications and Situations for Which Root Cause Analysis Requirements May Be Relaxed). This Task does not name who takes that decision, which Implementation 3.9.1: Establish Accountable Ownership covers.

Trustworthiness Side Effects to Consider:

  • Secure: The safety margins set under Implementation 8.2.2: Identify Opaque Systems and Appropriate Safety Margins, and the list of systems they apply to, show how far an SI system can be pushed before control passes to a fallback. An attacker could use them to keep a manipulated system just inside its margins, so that the hand-off never triggers. Protecting them is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Safe versus any characteristic the SI system was deployed to improve, including Safe itself: Where the SI system seldom approaches its safety margins, wide margins cost little. Where it operates near them, frequent hand-off to deterministic, legacy or manual operation gives up much of the benefit for which the SI system was deployed, which may include safety, and adds to operator workload. Options include setting margins relative to a verified-safe legacy system, where one exists, as in Implementation 8.2.1: Identify Applications and Situations for Which Root Cause Analysis Requirements May Be Relaxed, so that each hand-off returns operation to a known baseline.

Related AI RMF Subcategories Include:

  • MANAGE 1.3 (on responding to high-priority risks): This Task covers response options for the risk that a failure cannot be traced to its cause, from substitution through compensating controls to safety margins with handover; it does not cover identifying which systems carry that risk. For that, see for example Implementation 8.1.2: Identify SI Systems that May Not Satisfy Root Cause Analysis Requirements.
  • MANAGE 1.1 (on authorizing the system): This Task informs the decision whether to deploy or re-commission an AI system whose failures cannot be traced deterministically; it does not cover the broader determination of whether the system achieves its intended purposes. For that, see for example Practice 1: Establish Requirements for Success.

Decisions for the Organization:

  • Where a safety obligation the organization has identified calls for root cause analysis, is the system deployed with compensating controls or substituted?
  • How wide are the safety margins, given the benefit a hand-off gives up? (see the tension in Task 8.2: Identify Additional Controls that May Be Required in Scenarios Where Deterministic Root Cause Analysis Is Not Possible)
  • What does the organization operate on while an SI system whose failure has no known cause is re-validated, and what happens if no fallback is prepared?

References:

  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Section 2.3.7, Safety Systems, describes the safety instrumented system, designed in accordance with IEC 61511, as often independent of all other control systems so that a failure of the basic process control system will not impair its function. Written for process safety, it is a sector example of a compensating control whose effect does not depend on the system it guards against, here an SI system whose failures cannot be traced to a cause.
