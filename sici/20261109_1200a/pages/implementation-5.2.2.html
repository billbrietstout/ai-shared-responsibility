Implementation 5.2.2: Action-Level, Context-Aware Authorization Policies

Checking each consequential action when it is taken helps an organization account for what has changed since access was granted, such as a new task or exposure to untrusted content. Evaluate and authorize individual AI actions (such as invoking tools, modifying setpoints, or executing financial transactions) at runtime before execution. Authorization checks should evaluate the requesting AI agent’s identity, current task scope, parameter limits, operational state (drawn from sources other than the requesting SI system’s own account of it), and any required human approvals. An authenticated session or prior authorization should not grant blanket permission for subsequent commands. Parameter limits can apply to the cumulative effect of a series of actions as well as to each action, so that small changes that are each permitted do not add up to one that is not. Context can narrow authority as well as grant it, for example by withdrawing an agent’s write access while the data it relies on is flagged as stale or inconsistent, or after it has processed untrusted content. Where human approval is required, bind it to the specific action and parameters approved, so that it does not carry over to a different or later command.

If an action is unauthorized or authority cannot be verified, the system should block the request or transition to a pre-defined safe state (see Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior). This means that an authenticated AI agent with general system access still needs explicit authorization for each specific consequential command. This Implementation decides whether a specific proposed action is permitted at the moment of execution. That is a different question from whether the requesting entity is permitted to interact with the system at all, which is established elsewhere in Practice 5: Implement Identity and Access Management (IdAM) for SI Agents, Systems, and Tools, and in Task 7.4: Define Authorization and Access Controls for SI Modifications for people modifying AI systems. It is also a different question from whether the SI system was fit to deploy at all, decided before runtime from its supply chain and provenance (Implementation 6.1.2: Require SIBOM for Mission-Critical Applications). Each is needed, and none substitutes for the others.

Decisions for the Organization:

  • Which actions need human approval, and which parameter and cumulative limits apply to the rest?
  • Which sources supply the operational state that authorization checks rely on?

References:

  • Guidance NIST SP 800-207, Zero Trust Architecture, from NIST. Section 2 defines zero trust around least privilege per-request access decisions taken in a network treated as compromised. The tenets in Section 2.1 include that authentication and authorization to one resource will not automatically grant access to a different resource, which is the principle that this Implementation extends to individual actions within an authenticated session.
  • Guidance NIST SP 800-162, Guide to Attribute Based Access Control (ABAC) Definition and Considerations, from NIST. Section 2.2 gives the working definition: an access decision computed by matching subject attributes, object attributes and environment conditions against a policy. Environment conditions are the dynamic factors independent of subject and object, which is the mechanism by which operational state enters a decision taken at the moment of the request.
  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM03:2026, Excessive Agency, gives complete mediation among its mitigations: authorization implemented in logic rather than left to the LLM to decide, with each request to a downstream system validated against security policy by the tool, by an independent pre-execution policy decision point, or by the downstream system itself. This bears on where the runtime check in this Implementation is enforced.
  • Guidance Agentic Identity and Access Management, Workstream 4: Secure Design Patterns for Agentic Systems, version 1.0, 20 March 2026, from the Coalition for Secure AI, an OASIS Open Project. Section 3.4, Authorization and delegation, asks that permissions be re-evaluated continuously, enabling privilege reduction when risk changes, and that high-impact or irreversible actions require human-in-the-loop or step-up controls. This bears on context that narrows an agent’s authority and on approval tied to the specific action.
