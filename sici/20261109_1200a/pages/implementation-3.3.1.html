Implementation 3.3.1: Context-Specific Failure Modes

Matching each application’s failure notification to its consequences helps operators notice the failures that matter without being flooded by those that do not. Conduct an engineering assessment for each application to determine its failure notification requirements. For example, silent resilience (e.g., automated retries or soft failovers) may be appropriate for non-critical administrative tasks where internal algorithmic recovery does not alter physical processes or mask safety margins. Conversely, for safety-critical IT/OT/ICS applications, a ‘fail loudly’ protocol should be enforced with explicit human notifications, even if the system continues to operate, perhaps in a degraded capacity. Set the priority of each such notification from the consequence if the operator does not respond. When setting the point at which it is raised, allow for the time that response takes. The assessment should include failures that do not announce themselves, for example an SI system producing confident output on inputs outside the conditions it was validated for, a display that continues to show the last output after the SI system has stopped updating it, or a change in behavior after a vendor update to an acquired SI system. For each, record how the failure would be detected and how long detection would take. Where the organization already performs a process hazard analysis (PHA) or failure mode and effects analysis (FMEA), this assessment can extend that analysis with SI-specific failure scenarios rather than starting a separate one.

These notification states should be programmatically linked to the independent safety wrappers in Task 3.2: Implement Independent Guardrails for SI Outputs so that an unacknowledged ‘loud’ failure automatically forces a transition to a deterministic fallback state (per Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior). To limit alarm floods and alert fatigue, utilize containment techniques such as time-delay hysteresis, dynamic deadbands (control and sensor ranges where minor fluctuations are ignored and assumed to be noise), and state-based alarm aggregation to compress rapid automated iterations into a single operational event change. See Task 4.4: Attention Governance and Alert/Alarm Flood Mitigation for further details.

Decisions for the Organization:

  • For each application, is silent recovery acceptable, or should it fail loudly? (see the Resilient versus Transparent tension in Task 3.3: Establish Failure Notification Requirements)
  • What priority does each notification carry?

References:

  • Guidance Health and Safety Executive (2000) Better alarm handling, Chemicals Sheet No 6, from Great Britain’s workplace health and safety regulator. For effective alarm prioritization, it advises using about three priorities and basing them on the potential consequences if the operator fails to respond. This is the basis for the priority of a loud failure set here.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. Section 6.3.1, Anomalies and Events, notes that OT components are often remote and not continually staffed, so a threshold may need to be set to alert earlier to allow for the expected response time. This bears on the point at which a loud failure is raised. Section 4.1.1, Framing OT Risk, suggests that organizations may consider incorporating cyber attack and IT failure scenarios into their process hazard analysis (PHA) or failure mode and effects analysis (FMEA) processes. This is the precedent for extending an existing hazard analysis with SI-specific failure scenarios here.
  • Research Bransby, M. L., and Jenkinson, J., The management of alarm systems, Contract Research Report 166/1998, funded by the Health and Safety Executive, Great Britain’s workplace health and safety regulator. Appendix 12 reports that no site visited used more than three normally displayed priorities, and that an approach-to-trip alarm may outrank the trip itself if the operator can still act. Section 5.3.2 and Appendix 10 describe deadband, de-bounce timers, shelving and single line annunciation for repeating alarms. These bear on the priorities and containment techniques set here.
