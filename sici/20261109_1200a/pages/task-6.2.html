Task 6.2: Align SI and Existing CI Asset Lifecycle Management

Externally sourced AI components should be integrated into asset lifecycle management, building on established processes where they exist. This helps keep each component’s versions and changes visible over the long life of the equipment it serves. Authorized updates can then be managed through change control, and runtime telemetry can help catch and isolate unannounced behavioral shifts resulting from silent third-party model modifications. OT equipment often remains in service for 10 to 15 years or longer, while the models and hosted services it depends on can be changed or withdrawn by their providers on much shorter cycles that are unrelated to the host equipment. Where those changes go unrecorded, they may surface only as changed behavior in operation.

Main Trustworthiness Contributions:

  • Reliable: Contributes the record that keeps qualification evidence attached to a known configuration: model version, training data provenance and inference endpoint routed through change control, with re-evaluation on change (Implementation 6.2.2: Track Vendor Updates and Third-Party Entity Changes Through Change Management Process). This Task does not cover drift within an unchanged model, which Implementation 2.3.4 and Task 3.4 discuss.
  • Accountable: Contributes tracking of the counterparty itself, including acquisition, sub-processor change and end of support (Implementation 6.2.2: Track Vendor Updates and Third-Party Entity Changes Through Change Management Process), so the party carrying the procurement obligations stays identified. This Task does not cover creating those obligations, which Task 6.1: Develop Policies for SI Supply Chain Requirements covers.

Trustworthiness Side Effects to Consider:

  • Secure: The asset register in Implementation 6.2.1: Register Externally Sourced SI Components in Asset Management Systems records which SI components are in service, their versions, where they are hosted, which need vendor connectivity, and which assets they serve. An attacker could use it to match components to known weaknesses, to find SI functions present but disabled, or to target a vendor connection that a critical asset depends on. Protecting the register is a matter for the organization’s existing information classification and handling practice.

Trustworthiness Tensions to Balance:

  • Any characteristic a release could degrade versus any characteristic it would fix: Where a vendor release is a feature or model change, and the delay of reviewing it before deployment adds little risk, the review can guard against a change that quietly degrades safety, security, reliability or another characteristic. Where it carries a fix, such as to safety, security, accuracy or reliability, holding it defers that benefit, so Implementation 6.2.2: Track Vendor Updates and Third-Party Entity Changes Through Change Management Process describes an emergency path, where the organization has established one, with the update reviewed and recorded through the normal process as soon as practical afterward.

Related AI RMF Subcategories Include:

  • GOVERN 1.6 (on building the AI inventory): This Task registers externally sourced models, tools and services in the existing asset management system at acquisition; inventory alone does not detect change, so this Task pairs registration with change control and telemetry.
  • MANAGE 3.2 (on monitoring pre-trained model risks): This Task routes vendor model updates through change control and watches for unannounced version shifts; it does not cover behavioral drift within an unchanged model. For that, see for example Task 3.4: Monitor for Anomalous SI Behavior.
  • MAP 4.2 (on establishing risk controls for AI system components): This Task treats change management and runtime telemetry as the internal controls applied to third-party components; it does not cover controls at the physical process boundary. For those, see for example Task 3.2: Implement Independent Guardrails for SI Outputs.

Decisions for the Organization:

  • Is an emergency path established for vendor releases that cannot wait, and which releases qualify because delay is judged an unreasonable risk? (see the Any characteristic a release could degrade versus any characteristic it would fix tension)

References:

  • Guidance Foundations for OT Cybersecurity: Asset Inventory Guidance for Owners and Operators, 13 August 2025, from CISA, EPA, NSA and FBI with the cybersecurity agencies of Australia, Canada, Germany, the Netherlands and New Zealand. Step 5, Implement Life Cycle Management, asks organizations to define the life cycle stages of each asset, from acquisition through decommissioning. It also asks for policies that follow the organization’s change management process and require inventory updates whenever devices are introduced or removed, even under emergency change authority. This bears on bringing externally sourced SI components into the same lifecycle and change control.
  • Guidance NIST SP 800-82r3, Guide to Operational Technology (OT) Security, September 2023, from NIST. The section Comparing OT and IT System Security notes that IT components typically have a lifetime on the order of three to five years, while deployed OT technology often lasts on the order of 10 to 15 years and sometimes longer. The discussion of OT cybersecurity program content adds that an OT system’s lifespan can exceed 20 years, so legacy systems may contain hardware and software that vendors no longer support. This bears on the mismatch this Task manages.
