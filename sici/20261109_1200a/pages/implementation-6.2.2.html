Implementation 6.2.2: Track Vendor Updates and Third-Party Entity Changes Through Change Management Process

Where possible, route vendor-issued updates and third-party configuration changes through the organization’s standard change management process, helping ensure updates are reviewed and approved before deployment rather than applied silently. Where the deployment model does not allow an update to be gated, such as for cloud-hosted and vendor-managed models, document that as a known limitation and monitor the provider on an ongoing basis. Where earlier versions are not kept available, records of decisions made before the change may become hard to interpret (see Task 10.1: Define Decision-Level Logging and Metadata Retention Policies). Sometimes an update cannot wait for the full review, because the delay would itself create an unreasonable risk. Where the organization has established an emergency path like the one in Implementation 7.4.1: Define and Implement Requirements for Approvals and Logging of Updates and Changes to SI Systems, route such an update through it, so that the update is reviewed and recorded through the normal process as soon as practical afterward. Where no such path exists, options include deferring the update, landing it under containment as in Implementation 6.1.1: Add SI Disclosure to Existing Procurement Policies where staging and tightened safety wrappers have been prepared, or suspending the SI system, each with its own considerations, such as continued exposure to the fault the update fixes. Some frameworks, such as SP 800-53’s CM-3, keep urgent changes within change control.

Combine required disclosures, as discussed in Implementation 6.1.1: Add SI Disclosure to Existing Procurement Policies, with runtime monitoring and telemetry, as discussed in Task 3.4: Monitor for Anomalous SI Behavior, to detect unannounced behavioral shifts after the fact, rather than treating the component as static. Asking at procurement whether the vendor allows a model version to be pinned, so that updates are adopted deliberately rather than pushed, can show in advance whether such gating will be possible. Comparing each new AIBOM received under Implementation 6.1.2: Require SIBOM for Mission-Critical Applications with the one recorded for the version in service can also reveal changes in base model, training data or external services that the vendor did not announce.

Changes to track include model version, training data provenance, inference endpoint, vendor-controlled configuration such as system prompts and guardrail or threshold settings, a change of the foundation model provider behind the same product, and change to the third-party entity itself, such as acquisition, sub-processor change, or end of support. Changes should trigger re-evaluation under Implementation 2.3.4: Recurrent Risk Evaluations.

The depth of that re-evaluation can scale with consequence. For example, a library fix with no change in behavior may follow a standard path, while a new model version in a function that can affect setpoints or alarms can be tested against the same representative operating scenarios as its predecessor, including upset conditions, compared with it, and reviewed by whichever role the organization assigns to approve changes to that function. The process or safety owner knows the consequences of the function best, and also carries pressure to keep it in service. Record who reviews and why. Where one person has to both own the function and approve its changes, for example in a small organization or a specialized function with few qualified reviewers, record that and how the conflict is offset, such as by a second reviewer for safety-affecting changes (Implementation 3.9.6: Keep a Record of Design Decisions and Accepted Risks). In particular, newly released or substantially revised models and other system components, AI or otherwise, warrant elevated monitoring and testing for a defined period after adoption. Treat these as a distinct category with a documented exit criterion for returning them to routine monitoring. This includes tools, libraries and other dependencies that an agent invokes: an automatic version update to a tool can change what the agent produces while the agent stays entirely within its authorized scope, so access monitoring alone will not reveal it.

Where the organization hosts the component, keeping the previous release available, with its hash recorded in a protected location, supports reverting to the last known good state if an update introduces problems. Reverting carries its own considerations, such as reintroducing faults the update fixed or losing compatibility with components that have since changed. Implementation 7.4.1: Define and Implement Requirements for Approvals and Logging of Updates and Changes to SI Systems sets the equivalent requirement for changes to internally sourced components.

Decisions for the Organization:

  • Which role approves changes to each safety-affecting function, and how deep is the re-evaluation for each kind of change?
  • How long does elevated monitoring of a newly adopted component last, and what is its exit criterion?
  • How long are earlier vendor releases and their SIBOMs kept, so that past decisions stay interpretable and reverting stays possible?

References:

  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control CM-3, Configuration Change Control, reviews and approves or disapproves configuration-controlled changes with explicit consideration of impact analyses, including unscheduled or unauthorized changes. Control SA-9, External System Services, applies where the organization has no direct control over a provider’s implementation of the required controls and calls for processes to monitor the provider’s compliance on an ongoing basis, which is the situation of a cloud-hosted model whose updates cannot be gated.
  • Guidance Deploying AI Systems Securely: Best Practices for Deploying Secure and Resilient AI Systems, Cybersecurity Information Sheet, version 1.0, April 2024, from the NSA Artificial Intelligence Security Center with CISA, the FBI and the national cybersecurity centers of Australia, Canada, New Zealand and the United Kingdom. Under Validate the AI system before and during use, it asks for hashes of each release of the AI model to be archived in a tamper-proof location, and for automated rollbacks so that the organization can revert to the last known good state. Under Update and patch regularly, it asks for a full evaluation before a new model version is redeployed. This bears on re-evaluating and reverting vendor updates.
  • Guidance OpenSSF Model Signing (OMS) Specification, Version 1.0, from the AI/ML Working Group of the Open Source Security Foundation, a cross-industry body hosted by the Linux Foundation; checked against commit 91bf841, October 2026. It defines a detached signature over every file in a model directory, made with a bare key, a certificate chain or Sigstore keyless signing (Section 4.1), so that the organization can confirm that an update came from the vendor and was not altered on the way. This bears on checking vendor-issued model updates before they enter change management.
