Implementation 3.2.2: Define and Independently Enforce Deterministic Operational Constraints

Constraints enforced outside the SI system help keep operation within safe limits however the SI system arrived at its output, including when that output is convincing but wrong. Define the boundary that the AI system should remain within for safe operation. These might be in- and out-of-range values, semantic and behavioral constraints, rate-of-change violations, and deterministic logical constraints that should be respected regardless of the AI system’s confidence score. These deterministic constraints should be defined and enforced independent of the AI system’s internal logic (e.g., via out-of-band safety wrappers, intermediate deterministic command validation proxies, or hardware interlocks at the physical process boundary). Each constraint should be sufficient for safe operation without reference to values the AI system generates about its own output, such as confidence scores, self-reported certainty, or model-generated risk scores. Such values may inform additional responses, such as escalation to an operator, but a constraint should not depend on them, so that a missing, inaccurate, or manipulated value cannot affect it. A violation of any one constraint should also not be offset by satisfying others or by a favorable aggregate score; voting or weighted scoring across measures may still inform advisory outputs, but not whether a constraint holds. Independence also applies to what the safety wrapper runs on: where consequence warrants, it should share as little as practical of its compute platform, power supply, and network path with the SI system, and record what it does share, so that a single fault is less likely to disable both (see How Far to Go and Implementation 3.5.2: Identify Indirect Shared Infrastructure and Collateral Damage Exposure). The same independence applies to the inputs and settings the safety wrapper relies on. A constraint checked against the same sensor readings that the SI system uses can be misled by the same faulty or spoofed reading. Where consequence warrants, the check should draw on an independent measurement. A constraint whose limits the SI system can change, directly or through a tool it can call, does not constrain it. Where this independence cannot be demonstrated, document the dependency and the compensating controls that cover it.

This out-of-band architecture helps keep constraint enforcement active even during model failures, prompt injections, or autonomous agents exceeding their intended constraints. These constraints should reflect the most restrictive combination of the organization’s, equipment’s, application’s, and the AI system’s safe operating limits (including the limits of the AI system’s training). Where the process already has hazard analyses, safety instrumented system cause-and-effect documentation or protection settings, these limits should draw on them. Record for each constraint the document it was derived from and its owner, so that a change to that source can prompt review of the constraint. Test the enforcement of each constraint with commands just inside and just outside its limits, at commissioning and after changes to the SI system, the constraint set or the control logic, in an environment selected under Implementation 1.3.2: Categorization of Testing Environments. Constraints should apply uniformly to all non-protective command sources at the physical process boundary, including AI recommendations, automated agents, remote operator sessions, and any other upstream system. Commands from protective functions, such as protective relay trips, safety instrumented system (SIS) shutdowns and emergency stops, should reach the actuator directly rather than pass through a safety wrapper that could intercept, delay or block them, since a wrapper on that path would add a new way for a protective command to fail to arrive. Where a simple stop would itself be unsafe, such as in a dynamically unstable process, or a bipedal humanoid robot that would collapse rather than fall in a controlled way (Implementation 3.2.3: Specify Fail-Safe States and Fallback Behavior), a stop request may instead go to logic that carries out a safe shutdown sequence. That logic then acts as a protective function itself. It may meet the definition of SI, for example where it plans a path to a fail-safe state or a controlled fall, but it should be far less complex than the SI system it backs up, and independent of it and verified to the standard expected of a protective function. Where a wrapper works by granting permission for actuation, confine that permission to non-protective paths, so that loss of the wrapper removes permission for SI-driven or optimizing commands without impairing protection.

Authentication and physical safety are separate concerns: confirming who or what sent a command (addressed in Practice 5: Implement Identity and Access Management (IdAM) for SI Agents, Systems, and Tools) does not guarantee that the command itself is safe to execute. An authenticated source can still issue a damaging command through error, misconfiguration, or compromise. Absent an explicit, authorized override, such safety wrappers should intercept physically unsafe commands regardless of their source or underlying cause, other than commands from the protective functions described above. Where such constraints need to be lifted, e.g., to facilitate an experienced human engineer remotely dealing with a novel situation, they should be overridden explicitly, in accordance with emergency safety protocols that the organization has established in advance. For each constraint, define what the safety wrapper does with a command that would violate it, such as rejecting the command, holding the last value that satisfied the constraint, or passing the decision to an operator. Limiting the command to the nearest permitted value (clamping) is a further option that can itself be unsafe: the resulting command differs from what any source issued, and an SI system unaware of the change may continue to act as though its own command took effect. A command that satisfies every constraint can still be harmful, since the constraints capture only the hazards identified when they were written. The monitoring in Task 3.4: Monitor for Anomalous SI Behavior includes unusual behavior that remains within the constraints. Some frameworks, such as SP 800-160v1r1, set non-bypassable as a design criterion for protective mechanisms. Any override or bypass of a constraint, whether for an emergency, commissioning or troubleshooting, should be authorized, logged, limited in duration and visibly indicated to operators. Where the organization has an existing practice for bypassing safety functions, it can be applied to safety wrappers as well. An untracked bypass can remain in place after the work it was granted for.

The same principle of independently-enforced constraints applies beyond physical process control: for AI systems that generate or filter information rather than direct commands, the “constraint” may be one of required completeness or fidelity, independently enforced regardless of the AI system’s own judgment about what is relevant. For example:

  • An attacker gaining access to a plant human-machine interface (HMI) could issue setpoint commands indistinguishable from legitimate AI recommendations.
  • A valve controlled by an AI system might have constraints that the AI system may not have properly learned, such as not being opened and closed in quick succession, and not being opened at the same time as another valve.
  • A condition report summarization tool should be constrained to include information about every asset, even if the AI system judges a given condition not to be of concern.
  • An AI system routing high-volume transactions or processing patient records should be bounded by deterministic validation rules that block anomalous account or resource allocations (e.g., assigning an atomic resource to two entities), prevent unauthorized data aggregation, or flag out-of-bounds risk parameters prior to downstream operational execution.
  • An AI system executing automated financial trades or market transactions should be bounded by pre-trade risk controls, such as hard credit limits, maximum order value thresholds, and price collars, that deterministically block out-of-bounds orders before market entry, regardless of the model’s confidence score. Some obligations, such as 17 CFR 240.15c3-5, limit how an out-of-bounds order is handled and who controls these checks. The response to an out-of-bounds order, and whether a documented dependency is acceptable in place of independence, depend on the obligations that apply to the organization.
  • An AI system’s pressure setpoint recommendation should be restricted to a 10 to 30 PSI range before it reaches the physical system, by hard constraints to not exceed these limits regardless of its recommendation, with a safety layer that is not under AI control.

Decisions for the Organization:

  • For each constraint, what does the safety wrapper do with a violating command: reject it, hold the last value, pass it to an operator, or clamp it?
  • Where does consequence warrant separate infrastructure and an independent measurement, and where is a documented dependency with compensating controls accepted instead?
  • Who may authorize an override or bypass of a constraint, and for how long? (see the Safe versus Robust tension in Task 3.2: Implement Independent Guardrails for SI Outputs)

References:

  • Guidance Principles for the Secure Integration of Artificial Intelligence in Operational Technology, December 2025, joint guidance from nine national cybersecurity agencies across seven countries, led by the United States Cybersecurity and Infrastructure Security Agency. Section 4.1 directs establishing safe operating bounds for OT devices and maintaining a known good state, or thresholds for safe behavior, against which departure can be recognized. Section 4.2 covers failsafe mechanisms that let an AI system fail without disrupting critical operations, including how to bypass or replace it. Section 2.4 lists challenges in AI-OT integration and, among the steps to mitigate them, failsafe mechanisms that revert to traditional automation or to manual operation for any SI-enabled process.
  • Standard ISA/IEC 62443-3-3, SR 3.5 (Input Validation), SR 3.6 (Deterministic Output), and SR 3.4 (Software and Information Integrity), from the International Society of Automation and the International Electrotechnical Commission. The industrial control system requirements nearest to the input bounds, predictable output and integrity checks this Implementation places outside the AI system.
  • Guidance OWASP Top 10 for Large Language Model Applications, Version 2026, from the OWASP GenAI Security Project, a volunteer community project of the Open Worldwide Application Security Project. LLM01:2026, Prompt Injection, covers the input boundary and asks that every model response be validated against a strict output schema in trusted application code before any downstream system acts on it, using structural validation rather than a second model call, and that credentials and state-change capability be held in application code with privileged calls routed through a deterministic policy engine that revalidates intent and arguments at execution time. LLM10:2026, Improper Output Handling, covers the output boundary, and LLM03:2026, Excessive Agency, covers the consequences of model output reaching privileged actions.
  • Regulation 17 CFR 240.15c3-5, Risk management controls for brokers or dealers with market access, a rule of the United States Securities and Exchange Commission codified in Title 17 of the Code of Federal Regulations. Paragraph (c)(1)(i) requires controls that reject orders exceeding pre-set credit or capital thresholds, and paragraph (c)(1)(ii) controls that reject orders exceeding price or size parameters. Paragraph (d) places those controls under the direct and exclusive control of the broker or dealer, which is the regulated form of the separation this Implementation asks for between the system that produces an action and the layer that permits it.
  • Guidance NIST SP 800-53r5, Security and Privacy Controls for Information Systems and Organizations, from NIST. Control SI-10, Information Input Validation, checks system inputs against specified definitions, including numerical range and acceptable values, which is the control-catalog form of the range and value constraints this Implementation enforces on AI-issued commands at the receiving system. Control AC-25, Reference Monitor, is written for the mechanism that enforces access control policy, but the design properties it specifies, tamperproof, always invoked, and small enough to be subject to analysis and testing, are the ones this Implementation wants of an independent safety wrapper that does not trust a command because of its source.
  • Guidance NIST SP 800-160v2r1, Developing Cyber-Resilient Systems: A Systems Security Engineering Approach, from NIST. Section D.5.2.3, Contain and Exclude Behaviors, holds that analysis of the mission can identify behaviors that are always unacceptable and others that are acceptable only under specific circumstances, and that excluding them prevents undesirable consequences. Exclusion can be done in advance, with trade-offs between assurance and flexibility, or by interrupting behavior on the basis of ongoing monitoring. This matches the structure of the constraints this Implementation defines, and the trade-off it names is the Safe versus Robust tension in Task 3.2.
  • Guidance NIST SP 800-160v1r1, Engineering Trustworthy Secure Systems, from NIST. Their Section D.4.2, Essential Design Criteria for Mechanisms, states that mechanisms must be non-bypassable, evaluatable, always invoked and tamper-proof, and that a design for any control function that provides protection should generally adhere to these criteria. Their Table 3 extends tamper-proof to the data the mechanism depends on, which cannot be modified in an unauthorized manner. This supports treating the inputs and settings of the safety wrapper as part of its independence here.
