Implementation 1.4.4: Requirements for SI-Generated Code, Configurations, Procedures, and Other Logic

Success criteria that reflect what experienced staff know, as well as what is written down, help generated code, configurations, and procedures fit how the site actually works. For AI systems that generate artifacts that affect execution, including by other systems (e.g., code and configurations) and by people (e.g., procedures, summaries of manuals), set success criteria that capture both formal documented specifications and as much of the relevant tacit institutional knowledge as practical.

Tacit knowledge is often unwritten. Experienced staff may be unaware of all they know, but they can often explain why they acted as they did. Asking them to explain past decisions can help bring this knowledge into the success criteria. Converting it into written criteria generally takes repeated dialogue among the people who hold it. For generated code, formal criteria can include a check that each software package it references is a known, intended dependency. Code-generating AI systems can reference packages that do not exist, and a name that does resolve may not be the package intended: it may be an unrelated or unmaintained package with a similar name, or a malicious one that an attacker has published under that name. A check that the package merely exists is therefore not sufficient. For validation of the generated artifacts against these criteria, see Implementation 12.2.3: Validation Against Tacit and Formal Requirements. For generated code and configurations, the formal specifications can include the target language or dialect, the platform and firmware version that it will run on, and site naming conventions.

Decisions for the Organization:

  • Which generated artifacts need validation before use, and how is the rigor of that validation set?

References:

  • Research Nonaka, I., “A Dynamic Theory of Organizational Knowledge Creation”, Organization Science 5(1), 14-37, February 1994. Section 2.2 draws on Polanyi to describe tacit knowledge as personal, rooted in action and context, and hard to formalize and communicate. Section 2.4 calls the conversion of tacit into explicit knowledge externalization, triggered by successive rounds of meaningful dialogue, and Section 3.2 describes it as a difficult process involving repeated, time-consuming dialogue. This bears on writing tacit knowledge into success criteria.
  • Guidance NIST IR 8367, Psychological Foundations of Explainability and Interpretability in Artificial Intelligence, from NIST. Section 4.1.3 draws on engineering management literature on the tacit nature of expertise. It notes that human experts may not be consciously aware of how they obtained an outcome, yet are often able to describe why they did what they did, and that experts can be queried for their rationales. This bears on eliciting the tacit institutional knowledge that this Implementation asks success criteria to capture.
  • Research Spracklen, J. et al., “We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs”, 34th USENIX Security Symposium, 2025. Section 1, Introduction, describes package hallucination, in which generated code recommends or references a package that does not exist, and how an adversary can publish a malicious package under that name. The abstract reports average hallucinated-package rates of at least 5.2% for commercial models and 21.7% for open-source models. This bears on the formal criteria for generated code in this Implementation.
